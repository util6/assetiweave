定位到了**两处已用对照实验确认的对话渲染缺陷，以及 Skill 列表的一处高优先级绘制风险**。这不是简单增加骨架屏或预渲染数量就能解决的问题。

## 一、已确认的问题

### 1. 对话预览没有真正受限的“视口”

关键位置：
- [会话工作区]( /Users/util6/code-space/assetiweave/frontend/src/pages/conversations/ConversationsPage.tsx#L2867 )只设置了 `min-h-[680px]`。
- [QuestionPreview]( /Users/util6/code-space/assetiweave/frontend/src/pages/conversations/ConversationsPage.tsx#L3283 )使用 `min-h-full`，而不是明确高度。

**最小高度不等于固定高度，也不约束内容继续撑开容器。**

我用真实组件和仓库已有的 80 轮对话压力数据，在 1280×820 的浏览器窗口中测得：

| 实验 | 内部滚动视口高度 | 挂载的轮次数 |
|---|---:|---:|
| 原始会话工作区 | 36,343px | 80 |
| 修正高度约束链 | 469px | 4 |

另外，在明确为 600px 高的父容器中，**仅给 QuestionPreview 增加 `height: 100%`**，内部视口就从 36,343px 降至 503px，挂载数量从 80 降至 4。

原来的实际链路是：

> 内容撑大容器 → 虚拟列表误认为几万像素都是可视区 → 几乎全部挂载 → 内部滚动检测也失去意义。

这是已经复现的结构性缺陷。

### 2. 虚拟窗口更新晚于滚动位置，骨架也会一起缺席

[VirtualizedCollection 第 184 行](/Users/util6/code-space/assetiweave/frontend/src/components/common/rendering/VirtualizedCollection.tsx#L184)显式设置了：

```tsx
useFlushSync: false,
```

在**先修正高度**的前提下，我执行了相同的 16 次大跨度跳转，每次采样 3 帧：

| 配置 | 48 个采样帧中，完全没有虚拟行覆盖视口的帧数 |
|---|---:|
| 当前 `false` | 15 |
| 仅改为 `true` | 0 |
| `true` 重复实验 | 0 |

机制是：

> 滚动位置已经改变，但 React 尚未提交新位置的虚拟行；旧行已离开视口，新行还没出现。

**骨架位于虚拟行内部。虚拟行尚未提交时，加再多骨架逻辑也填不上这个缺口。**

这里证实的是逐帧 DOM 覆盖缺口；截图中的原生 WebKit 瞬态绘制表现，还需要在桌面应用中验收。

## 三、为什么以前的修复效果不好

此前的方向主要是“不透明表面＋虚拟化＋骨架调度”，但遗漏了前提：

1. **虚拟化需要正确且有限的视口高度。**
2. **骨架需要对应的虚拟行及时提交。**
3. **Skill 列表并未接入这条修复链路。**
4. **局部不透明背景并不等于消除了外层绘制负担。**

我运行了现有渲染相关测试：**9 个文件、22 个测试全部通过**。但测试把视口高度模拟为固定的 240px，部分测试只检查 CSS 字符串，因此没有覆盖真实布局失控和逐帧空白。

## 四、建议的修复顺序

### 第一阶段：修复已经证实的两处缺陷

**① 建立完整的高度约束链和明确的滚动归属。**

```text
有明确可用高度的工作区
  → 分栏容器
    → h-full / min-h-0 的预览根节点
      → shrink-0 的标题区
      → min-h-0 / flex-1 的内部滚动区
```

正式实现应使用窗口剩余空间，而不是写死实验中的 600px；同时覆盖问题列表展开、收起两种布局。

**② 恢复虚拟列表默认同步提交。**

删除 `useFlushSync: false`，或显式设为 `true`。同步保证轻量虚拟行和骨架及时到位，复杂 Markdown、Diff 仍保留延迟渲染。

### 第二阶段：降低 Skill 列表的绘制负担

- 去掉**长列表整体和重复行操作区**的背景模糊，使用主题色、渐变、边框保留视觉风格。
- 玻璃效果优先留在尺寸有限的固定工具栏。
- 给资产列表建立明确滚动区域，再按数据规模引入虚拟化。
- 暂不同时叠加更多 `translateZ(0)`、`will-change` 或 containment 补丁，以免干扰归因。

### 第三阶段：用真实渲染验收

必须覆盖：

- 原生 Tauri/WebKit 中快速往返拖动滚动条；
- 130／1,000 条资产和长对话；
- 每个采样帧都有内容或骨架覆盖视口；
- 挂载数量随视口变化，而非随总数据量增长；
- 展开长文本、调整列宽、搜索跳转后没有明显高度跳动。

**本次没有修改业务代码，也没有动已有未提交改动。最值得先落地的是“高度约束链＋虚拟窗口同步提交”，这两项已经有明确的实验依据。**

**两者限制的不是同一个高度。而且，单独修复高度约束链，不足以保证快速上滑不再出现空白。**

你补充的现象很关键：**向下逐步加载已经改善，但快速返回已浏览内容仍然出问题，说明“限制加载量”没有解决滚动时内容及时显示的问题。**

## 1. 两个方案的本质区别

按你的描述，之前的方案更接近**渐进增加可滚动内容**：

> 先开放一段内容，滚到底部后，再渲染下一段。

它限制的是：**现在允许滚到多远、已经加载多少内容**。

我说的高度约束链限制的是：**显示内容的窗口有多高**，而不是整篇内容有多高。

例如：

```text
预览窗口高度 clientHeight：600px，保持稳定
全部内容高度 scrollHeight：50,000px，可以继续增长
```

即使整篇内容非常长，真正的预览窗口仍然只有 600px。虚拟列表据此判断应该挂载哪些行。

| | 你描述的旧方案 | 高度约束链 |
|---|---|---|
| 控制对象 | 已开放的内容范围 | 实际可视窗口 |
| 到底后 | 增加后续内容 | 窗口高度不变 |
| 主要作用 | 限制一次加载量 | 让虚拟化正确计算可视范围 |
| 快速向上回跳 | 仍可能出现空白 | 单独使用仍可能出现空白 |

**两者可以同时存在，但彼此不替代。**具体到之前那次提交，还需要核对代码，确认它限制的是内容范围还是视口本身。

## 2. 为什么快速上滑仍然会空白？

这里有一个容易混淆的点：

**内容之前加载过，不代表现在仍有对应的 DOM，更不代表浏览器已经准备好绘制它。**

虚拟列表通常会卸载远离视口的行。快速向上跳转时，可能发生：

```text
滚动位置已经跳到上方
        ↓
上方的行之前已被卸载
        ↓
React 尚未提交新的虚拟行
        ↓
这一帧只有背景，连骨架都没有
```

这和“到底后再加载下一段”没有直接关系。即使所有数据都已经在内存中，也可能出现。

**本次实验中，在修正高度之后，我仍然复现了这个缺口。**所以，高度约束确实不是完整答案：

- 高度修正，但保留 `useFlushSync: false`：48 帧采样中，15 帧没有虚拟行覆盖视口。
- 再仅改为 `true`：相同采样未覆盖次数为 0，重复实验也是 0。

这也是我提出第二项修复的原因：**窗口尺寸正确，还需要新位置的虚拟行及时提交。**

## 3. 那么，这次方案到底能解决到什么程度？

准确地说：

### 已有证据支持解决的部分

**高度约束链＋虚拟窗口同步提交**，分别解决：

1. 虚拟列表错误地把整篇内容当成可视区；
2. 滚动位置变化后，新虚拟行提交滞后造成的覆盖缺口。

这两项不是同一种“限制高度”，也不是对旧方案换个名称。

### 仍需原生应用验证的部分

即使 DOM 已经覆盖视口，WebKit 也可能因为背景模糊、绘制负担或尺寸变化，暂时没有把内容画出来。

**如果空白发生时 DOM 已存在，那就应继续处理绘制层，而不是继续调整加载高度。**当前浏览器实验没有证明这一部分已经消失。

## 4. 我会怎样避免再次“修了一轮，效果仍不好”？

下一步应该直接以你说的场景作为验收：

> 向下浏览多段内容 → 快速向上拖回已浏览区域 → 连续往返。

空白发生时同时检查：

- **视口没有对应 DOM**：处理虚拟窗口更新。
- **有行框，但尺寸或位置不对**：处理测量、占位高度和滚动锚点。
- **DOM 和位置都正确，画面仍空白**：处理 WebKit 绘制与合成。

**结论：高度约束是必要的基础修正，不是“彻底解决快速上滑”的保证。完整方案需要同时修复虚拟窗口提交，并在原生 WebKit 中通过你这条复现路径验收；最终以画面不再出现缺口为准，而不是以 CSS 改完或单元测试通过为准。**

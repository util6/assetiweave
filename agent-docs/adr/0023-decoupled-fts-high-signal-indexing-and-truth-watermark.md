# 0023: 全文索引与同步解耦、高信号检索白名单与物理事实时间戳水线

> **状态**：已提议（修正 ADR-0021 关于单事务清理重写 FTS5 的约定，补齐 ADR-0022 子代理水线契约，拨正 Issue #104 索引下沉范围）  
> **决策日期**：2026-11-10  

---

## 一、 背景与业务意图澄清 (Context & Requirement Clarification)

在对会话同步（Conversation Sync）耗时劣化（实测高达 29.6 分钟）与底层 SQLite 锁竞争的排查中，我们深入溯源了 2026 年 10 月 23 日（Issue #104）、11 月 6 日（ADR-0021）与 11 月 9 日（ADR-0022）的架构演进。

事实表明，过去多轮迭代中系统引入了严重的“工程技术代偿”，偏离了最初朴素、优雅的产品业务初衷。经系统性讨论，明确以下五项核心业务意图的真实边界：

### 1. 增量判定粒度与水线依据 (Incremental Granularity & Watermark)
- **真意**：增量同步的判定粒度始终是 **Session**。无论 Session 内部发生轮次追加、编辑重生成或回滚（Rewind），只要该 Session 发生变动，将其全量覆盖重扫即可自然自愈；未变动的 Session 在最外层直接快速早退。
- **依据**：水线不依赖容易被外部操作系统触摸（Touch）的文件系统 `mtime`，而是**直接从本地物理存储（如 JSONL、Transcript 等）内部记录的真实业务时间戳字段取证**。以此为准进行单调时间戳比对，彻底摒弃多维哈希账本与观察表等过度设计。
- **边界（与规格对齐）**：`source_fingerprint` 是**不透明版本凭据**，仓储只做 `相等 / 不相等` 判断，不做全局单调时钟比较，也不把标题、路径、起止时间等展示属性纳入变更判定。判定规则只有一条：**没有成功指纹，或发现到的版本令牌与已落库指纹不同，就重扫**。

### 2. 增量写入与搜索索引的强弱边界 (OLTP vs Search Decoupling)
- **真意**：增量同步的核心职责是**业务事实入库（OLTP）**。将新会话的 Session、Turn、Part 写入 SQLite 是极轻量的操作（单会话耗时仅 3~5ms），写入完成即代表同步成功。
- **纠偏**：搜索索引是只读派生产物，绝不能与高频写入强行捆绑在同一个事务中；增量同步严禁在主事务内执行跨全表、全库的 FTS 索引扫除与重建。

### 3. 会话本地删除的“数据保险箱”定位 (Data Safe vs Realtime Reconciliation)
- **真意**：本地源文件被用户删除或跨设备迁移时，AssetIWeave 充当**只增不减的资产保险箱**——数据库资产严禁物理跟随删除，仅标记 `missing = 1` 作为离线兜底。
- **纠偏**：这是针对换新电脑或用户整理目录的**极低频防御性场景**，绝不是高频日常增量同步的实时指令。日常同步严禁为了“揪出谁被删了”而强制枚举全盘成百上千个文件，缺失对账必须彻底剥离到冷路径。

### 4. 子代理（Subagent）的水线可推导性 (Subagent Watermark Derivation)
- **真意**：Subagent 子会话也是合法的 Session，有明确的内部末轮时间戳。即使内联寄生于父会话，由于“父文件未动则子代理绝不可能动”，子会话天然可确定性继承父文件的水线标识（如 `parent_watermark#subagent_id`）。
- **纠偏**：禁止适配器以“非独立文件”为由偷懒返回 `source_fingerprint: null`，杜绝 370 个历史子会话沦为“永久无指纹、每轮必重导”的僵尸假变动。

### 5. 全文检索的“高信号白名单”（搜索噪音提纯）
- **真意**：Issue #104 时代为了“删除 Question 冗余表”，AI 附带引入的“零件级无脑全量下沉”是严重的历史失误——将终端数万行编译输出、命令 stdout、错误堆栈、中间推理日志塞入 FTS5，导致虚表膨胀至 30 多万行（267MB），既引发无索引全表扫描，又充斥垃圾噪音。
- **重构**：搜索索引严格收敛为**“四大高信号白名单”**（提问、回答、变更文件路径、命令标签），其余过程性噪音一概拒绝入库。

## 二、 架构决策 (Decisions)

基于上述澄清，系统做出以下四项根本性架构决策：

### 决策 1：入库主事务彻底剥离 FTS5 读写
- 修正 ADR-0021 中“在单事务内按会话整体清理并重写 FTS5 索引”的约定。
- 从 `replace_session_snapshot_sqlx_tx` 中**彻底物理移除**对 `conversation_part_fts` 的 `DELETE` 与 `INSERT` 操作。
- 会话整包写入回归纯粹的业务事实表（`conversation_sessions` / `turns` / `parts`），单会话写入事务耗时压降至 3~5 毫秒，SQLite 全局写锁微秒级释放。

### 决策 2：建立全文索引“四大高信号白名单”
索引写入端设立严格过滤器，仅允许以下四类高价值正文进入检索语料：
1. **用户提问正文（User Prompt）**；
2. **AI 回答正文（Assistant Answer）**；
3. **变更目标文件路径（Changed File Paths）**：仅提取文件变更卡片的目标相对/绝对路径与文件名，**严禁将数万行 patch / diff 正文原样塞入索引**；
4. **命令语义标签（Command Labels）**：仅提取高层执行意图标签（如“编译构建”、“单元测试”），**严禁将终端长篇 stdout / stderr 塞入索引**。

*其余所有中间推理、子代理委派明细、工具执行裸日志一律不进入 FTS5。索引总行数由 30 万行压降 80%~90%，体积骤降至数十兆。*

### 决策 3：物理事实时间戳水线与 Subagent 契约补齐
1. **真实数据源水线取证**：适配器提取 Session 的版本水线时，直接以本地存储（如 JSONL transcript）中真实数据行的单调业务时间戳为准；
2. **Subagent 契约规范**：所有适配器产出的 Subagent 会话必须携带有效 `source_fingerprint`：
   - 优先采用末轮实际结束时间戳 `turns.at(-1)?.ended_at`；
   - 内联子会话直接继承父会话水线复合值：`${parent_version_token}:subagent:${subagent_id}`；
3. **存量自愈迁移**：内联子代理会话的指纹只允许在**无歧义可推导**时回填——父会话已有成功业务指纹，且子会话带着稳定父键与稳定身份，此时派生 `${parent_fingerprint}:subagent:${subagent_external_id}`。父指纹缺失、父子关系不明或历史令牌不可信时保持 `NULL`，交给真正的重读去闭合水线；**严禁沿用 `updated_at` 或文件 `mtime` 伪造一个"成功版本"**，否则会把永久漏同步伪装成"已是最新"。

### 决策 4：冷热动静彻底分离管线
1. **热路径（日常增量同步，Hot Path）**：
   - 仅根据本地存储内部时间戳大于水线的条件，筛选真实发生变更的 0~2 个活跃 Session；
   - 仅执行业务事实入库，**完全不执行全盘文件枚举与 missing 对账**，端到端耗时控制在 **< 2 秒**。
2. **冷路径（缺失对账与索引整理，Cold Path）**：
   - **缺失感知（Lazy Check）**：用户在界面交互点击查看具体会话时，若磁盘文件缺失，就地标记 `missing = 1`；
   - **全量对账（Explicit Full Sync）**：仅在用户显式触发“全量同步”或“数据完整性体检”时，才慢速遍历全盘进行 missing 标记对账与 FTS 索引垃圾回收。

## 三、 备选方案与取舍 (Alternatives & Trade-offs)

- **弃用方案 A：加 `conversation_part_fts_map` 辅助映射表**：
  - *原因*：仅解决删除时的全表扫描，但未能解决 FTS 充斥 30 万行垃圾日志的信噪比问题，且依然把搜索维护绑死在写入主事务中，属于典型的代偿性打补丁。
- **弃用方案 B：修改 9 个适配器升级批量 RPC 接口**：
  - *原因*：跨仓库工程改动过大。只要日常增量水线被正确修复为仅漏入 1~2 个真实会话，外部读取本身的耗时就只有数秒，无需在现阶段大动干戈改造适配器通信协议。
- **弃用方案 C：纯操作系统文件系统 `mtime`**：
  - *原因*：操作系统文件 `mtime` 易被编辑器保存、git 分支切换或网盘同步误触；直接从物理存储（JSONL）取证内部时间戳既准确又扎根于数据事实。

## 四、 后果与系统影响 (Consequences)

### 正向收益
1. **彻底根治卡顿**：移出 FTS 后，会话入库写锁占用由 15 秒/次降至 3~5 毫秒/次，全应用彻底告别卡顿与发涩；
2. **增量水线闭合**：370 个历史子会话回填指纹后，日常增量同步只处理真正改动的会话，任务耗时由 **29.6 分钟缩减至 < 2 秒**；
3. **搜索体验质的飞跃**：剔除终端日志与巨幅 diff 噪音后，索引表行数骤减 80%~90%，全文检索命中率与精准度极大提升；
4. **资产保险箱机制归位**：数据迁移与防误删依然有效，但不再绑架日常增量同步。

### 演进与落地计划
1. **阶段 1（立即生效）**：在 `snapshot.rs` 中剥离 FTS 清理与写入，事实事务只写 `sessions / turns / parts`；父快照替换不再承担子会话物理清理。
2. **阶段 2（索引提纯）**：由 `domain::conversations::search_corpus` 的版本化策略统一生成"提问 / 最终回答 / 变更文件路径 / 命令语义标签"四类文档，FTS5 与独立搜索索引消费同一份文档；语料口径升级通过 `corpus_policy_version` 触发受控重建。
3. **阶段 3（适配器规范）**：定向读取收口为"唯一根会话 + 它声明的内联子会话"，内联子会话缺失指纹时由父水线确定性派生。
4. **阶段 4（管线分离）**：`ConversationSyncMode` 透传到仓储导入边界，Missing 对账只在 `Full` 执行；增量只按会话选变化。

## 五、 实施状态 (Implementation Status)

- **事实事务边界**：`replace_session_snapshot_sqlx_tx` 只写业务事实。FTS5 维护由事件消费者 `conversation.corpus_advance` 在事实提交后按"租户 + 会话"合并推进，单会话小事务、幂等替换、失败重试不反噬事实。
- **共享语料**：`SearchCorpusPolicy` 是唯一口径来源，`SearchCorpusDocument` 为后端中立文档；FTS5 与 Tantivy 的文档集合同源，独立索引的水合路径直接从已提交事实重算文档正文，不再回读展示卡片。
- **冷热分离**：`ConversationSyncMode::Incremental` 不做 missing / resurrect 对账；`Full` 只做标记，绝不物理删除。
- **保险箱语义**：父快照替换与子代理会话之间不存在隐式级联删除，源端消失只表达为 `missing = 1`。
- **存量升级**：`20261111000001` 只落"需要重建"的标记与可无歧义推导的子代理指纹；真正的索引重建由后台流水线按会话分批推进并在收尾时做一次 `OPTIMIZE`。

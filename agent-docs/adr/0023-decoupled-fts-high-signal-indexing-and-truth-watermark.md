# 0023: 会话业务水线、事实快照收口与 Tantivy 单一搜索索引

> **状态**：已采纳（修订 ADR-0021 的单事务 FTS5 维护约定，补齐 ADR-0022 子代理水线契约，拨正 Issue #104 的索引下沉范围；并把"双索引并存"修正为 **Tantivy 单一索引**）  
> **决策日期**：2026-11-10  

---

## 一、 背景与业务意图澄清 (Context & Requirement Clarification)

在对会话同步（Conversation Sync）耗时劣化（实测高达 29.6 分钟）与底层 SQLite 锁竞争的排查中，我们深入溯源了 2026 年 10 月 23 日（Issue #104）、11 月 6 日（ADR-0021）与 11 月 9 日（ADR-0022）的架构演进。

事实表明，过去多轮迭代中系统引入了严重的“工程技术代偿”，偏离了最初朴素、优雅的产品业务初衷。经系统性讨论，明确以下五项核心业务意图的真实边界：

### 1. 增量判定粒度与水线依据 (Incremental Granularity & Watermark)
- **真意**：增量同步的判定粒度始终是 **Session**。无论 Session 内部发生轮次追加、编辑重生成或回滚（Rewind），只要该 Session 发生变动，将其全量覆盖重扫即可自然自愈；未变动的 Session 在最外层直接快速早退。
- **依据**：水线不依赖容易被外部操作系统触摸（Touch）的文件系统 `mtime`，而是**直接从本地物理存储（如 JSONL、Transcript 等）内部记录的真实业务时间戳字段取证**。以此为准进行单调时间戳比对，彻底摒弃多维哈希账本与观察表等过度设计。
- **边界（与规格对齐）**：`source_fingerprint` 是**不透明版本凭据**，仓储只做 `相等 / 不相等` 判断，不做全局单调时钟比较，也不把标题、路径、起止时间等展示属性纳入变更判定。判定规则只有一条：**没有成功指纹，或发现到的版本令牌与已落库指纹不同，就重扫**。

### 2. 增量写入与搜索索引的强弱边界 (OLTP vs Search Decoupling)
- **真意**：增量同步的核心职责是**业务事实入库（OLTP）**。将新会话的 Session、Turn、Part 写入 SQLite 是极轻量的操作（单会话耗时仅 3~5ms），写入完成即代表同步成功。
- **纠偏**：搜索索引是只读派生产物，绝不能与高频写入强行捆绑在同一个事务中；增量同步严禁在主事务内执行跨全表、全库的 FTS 索引扫除与重建。

### 3. 会话本地删除的“数据保险箱”定位 (Data Safe vs Realtime Reconciliation)
- **真意**：本地源文件被用户删除或跨设备迁移时，AssetIWeave 充当**只增不减的资产保险箱**——数据库资产严禁物理跟随删除，仅标记 `missing = 1` 作为离线兜底。
- **纠偏**：这是针对换新电脑或用户整理目录的**极低频防御性场景**，绝不是高频日常增量同步的实时指令。日常同步严禁为了“揪出谁被删了”而强制枚举全盘成百上千个文件，缺失对账必须彻底剥离到冷路径。

### 4. 子代理（Subagent）的水线可推导性 (Subagent Watermark Derivation)
- **真意**：Subagent 子会话也是合法的 Session，有明确的内部末轮时间戳。即使内联寄生于父会话，由于“父文件未动则子代理绝不可能动”，子会话天然可确定性继承父文件的水线标识（如 `parent_watermark#subagent_id`）。
- **纠偏**：禁止适配器以“非独立文件”为由偷懒返回 `source_fingerprint: null`，杜绝 370 个历史子会话沦为“永久无指纹、每轮必重导”的僵尸假变动。

### 5. 全文检索的“高信号白名单”（搜索噪音提纯）
- **真意**：Issue #104 时代为了“删除 Question 冗余表”，AI 附带引入的“零件级无脑全量下沉”是严重的历史失误——将终端数万行编译输出、命令 stdout、错误堆栈、中间推理日志塞入 FTS5，导致虚表膨胀至 30 多万行（267MB），既引发无索引全表扫描，又充斥垃圾噪音。
- **重构**：搜索索引严格收敛为**“四大高信号白名单”**（提问、回答、变更文件路径、命令标签），其余过程性噪音一概拒绝入库。

## 二、 架构决策 (Decisions)

### 决策 1：事实事务零索引写入
- 修正 ADR-0021 中"在单事务内按会话整体清理并重写 FTS5 索引"的约定。
- `replace_session_snapshot_sqlx_tx` 只写业务事实（`sessions` / `turns` / `parts`），
  不读取、不写入任何检索索引；单会话事实写入保持在毫秒级，写锁即时释放。
- 父快照替换不对子代理会话做隐式物理清理，源端消失只表达为 `missing = 1`。

### 决策 2：版本化高信号语料是唯一检索口径
- `SearchCorpusPolicy`（`high-signal@N`）是唯一口径来源，输出后端中立的
  `SearchCorpusDocument`；只放行**用户提问、最终回答、变更文件路径、命令语义标签**。
- 终端输出、diff 正文、工具结果正文、推理日志、子代理委派明细一律不进入语料。
- 语料来自已提交的 Turn 与结构化 Part 事实，不读取任意展示卡片正文。
- 口径升级只能提升版本号，由索引代际记录 `corpus_policy_version` 并触发受控整代重建，
  绝不就地改写一代已发布的索引。

### 决策 3：业务水线与快照替换
- Session 是唯一的增量与快照替换粒度；`source_fingerprint` 是**不透明版本凭据**，
  仓储只做相等/不等比较，不做全局单调时钟比较，也不把标题、路径、起止时间纳入判定。
- 没有成功指纹或版本令牌变化即重扫；失败不推进水线。
- 定向读取返回"唯一根会话 + 它声明的内联子会话"，拒绝缺失/重复根、无关会话、
  重复、非法子指纹与根版本漂移；内联子会话缺指纹时由父水线确定性派生。

### 决策 4：Tantivy 是唯一的词法派生索引
- SQLite 的 Session/Turn/Part 是唯一业务事实，Tantivy 是唯一词法索引，
  FTS5 **不是**第二生产索引、也不是长期兜底。
- Tantivy 同时承载 Question/Card 文档与 Session 文档：Session 文档携带标题、
  项目路径、高信号聚合正文、租户/记录族、来源与适配器属性，以及父子归集所需的
  `parent_session_id` / `user_visible`。
- 卡片检索与列表检索共用同一份语料，因此同一关键词在两种入口给出同一口径的命中。

### 决策 5：事实提交后按变化会话增量推进
- 事实提交的 Outbox 事件继续作为派生索引的触发器，消费者按事件载荷里的
  `changed_session_ids` 合并去重，只读这些会话的最新已提交快照，删旧文档、写新文档、
  一次提交并刷新读取器。
- 未变化会话不被读取、不被重写；日常提交不再触发整租户重建。
- 变更集合超过可可靠承载的边界、或事件没有携带会话清单时，请求一次受控整代重建，
  绝不静默跳过。
- 消费者幂等：重放同一批次产出同一份当前文档集合，不产生重复文档；失败不推进
  持久 offset。

### 决策 6：索引不可用时回退到事实，而不是降级为标题
- Tantivy 缺失、构建中、过期、失败或损坏时，检索回退到 SQLite 已提交事实上的
  完整高信号扫描：先用事实列做超集筛选，再用同一份语料策略逐条确认。
- 回退可以更慢，但检索字段与语料语义不得收缩；**标题级降级被移除**。
- 索引与回退共享同一套筛选、父子归集、排序与分页契约，最终分页结果不依赖
  命中是哪个后端产出的。

## 三、 备选方案与取舍 (Alternatives & Trade-offs)

- **弃用方案 A：`conversation_search_doc_row` 辅助映射表**：
  - 曾经落地过：用于把 FTS5 的按会话删除从"扫描全部正文"降为 rowid 点查。
    它确实把删除从 8~19 秒降到毫秒级，但只是让一个本不该存在的索引更能用。
  - *弃用原因*：生产代码从未使用 FTS5 的 `MATCH`，索引只被子串查询当作正文列存储；
    实测同一个列表查询在 FTS5 上要 114 秒、在普通表上 0.12 秒。映射表连同 FTS5
    一并退役，不再保留任何 rowid 账本。
- **弃用方案 B：保留 FTS5 作为长期兜底**：
  - *原因*：两套索引意味着两套写放大、两套状态、两套一致性风险，而兜底能力可以用
    "事实回退"更正确地获得（口径完全一致、不会漏字段）。
- **弃用方案 C：纯文件系统 `mtime` 作为版本依据**：
  - *原因*：`mtime` 易被编辑器保存、分支切换或网盘同步误触；版本必须来自宿主真实
    业务记录。
- **弃用方案 D：适配器批量 RPC 重设计**：
  - *原因*：不属于本规格范围；水线修好后单次同步只会选中极少数真实变化的会话。

## 四、 后果与系统影响 (Consequences)

### 正向收益
1. **写入路径唯一**：事实事务零索引写入；派生索引只由消费者按变化会话推进，
   不再与同步抢同一把写锁。
2. **删除与重建可行**：FTS5 的按会话删除曾是同步被拖成分钟级、并撞出
   `database is locked` 的根因；删除 FTS5 后这条慢路径彻底消失。
3. **读路径变快**：列表正文匹配从"FTS5 逐行取列"（实测 114 秒 / 658 会话）变为
   索引命中 + 事实水合；索引不可用时走事实回退，仍然完整。
4. **口径单点**：同一份语料策略同时服务整代重建、增量推进与事实回退，
   三种模式不会给出不同的可检索性。
5. **保险箱归位**：数据迁移与防误删仍然有效，且不再绑架日常增量同步。

### 演进与落地计划（已完成）
1. **阶段 1**：事实事务剥离索引读写；`ConversationSyncMode` 冷热分离。
2. **阶段 2**：版本化高信号语料策略；内联子会话指纹由父水线确定性派生。
3. **阶段 3**：Tantivy 补齐 Session 文档；列表检索改为"索引给身份 + 事实水合"。
4. **阶段 4**：消费者按变化会话增量推进；超出边界退回受控整代重建。
5. **阶段 5**：索引不可用时的完整事实回退，移除标题级降级。
6. **阶段 6**：停写并移除 FTS5 链路，前向迁移删除 FTS5 主表、shadow tables、
   状态表与 rowid 映射表。

## 五、 实施状态 (Implementation Status)

- **单一索引**：`conversation_search_index_state` 是唯一的搜索状态与代际契约；
  `CorpusPolicyVersion` / schema 版本 / 分词器版本任一不一致即视为不可用并走出受控重建。
- **文档形状**：`load_conversation_search_index_documents_sqlx` 产出三类文档
  （`question` / `card` / `session`）；整代重建与增量推进共用同一个
  `document_from_row` 构造函数，避免两条路径产出不同形状。
- **增量推进**：`advance_conversation_search_index` 按会话 `delete_term + add + commit`，
  单批上限 512 个会话；超过上限或索引代际不可用时自动退回受控整代重建。
- **事实回退**：`search_session_ids_by_corpus_sqlx` 用事实列做超集筛选，再用语料策略
  确认；索引不可用时列表与卡片检索都走它，不再有"仅标题匹配"的分支。
- **状态收敛**：会话搜索只有一套状态与一套维护入口（`conversation.search.index.*`）；
  零件级索引状态、重建任务与 `OPTIMIZE` 随 FTS5 一起删除。
- **迁移**：`20261111000005` 删除 `conversation_part_fts`、`conversation_search_doc_row`
  与 `conversation_part_index_state`；历史 FTS 正文不迁移，Tantivy 由事实重建。
  迁移不执行 `VACUUM`，避免启动期全库重写。
- **保留的历史证据（former FTS 实现，不是新索引的目标）**：
  - 整代重建（1892+637 会话、26 万行存量索引）48 秒完成，索引规模 262,903 → 22,903 行；
  - `conversation_part_fts` 按会话删除 8~19 秒、按租户清空 9.5 秒（写锁独占）；
  - FTS5 列表正文匹配 114 秒 vs 普通表 0.12 秒——这条对照直接推动了"删除 FTS5"的决策。
- **读取路径的连接顺序（仍然有效）**：`conversation_parts` / `web_record_parts` 已有
  `UNIQUE (tenant_id, turn_id, part_index)`；`FROM parts JOIN turns ORDER BY p.turn_id`
  会让规划器选择"按 tenant_id 扫描全部零件"。必须写成 `FROM turns CROSS JOIN parts`
  固定轮次驱动，语料生成与事实回退都沿用这个顺序。
- **保险箱语义**：父快照替换与子代理会话之间不存在隐式级联删除。

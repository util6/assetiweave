# 0005: 适配器声明的会话卡片（Conversation Card）契约

> 状态：已接受
> 决策日期：2026-08-03
> 决策证据：`93f699b`
> 记录日期：2026-08-03

## 背景

会话卡片此前被限制在 5 种全局固定的类型中。相同的类型枚举列表重复出现在适配器脚本、Rust DTO 与 Repository、搜索索引、前端渲染、过滤器、国际化翻译、主题配色和导出逻辑中。由于不同的 AI 应用具有不同的语义记录，扩展该列表需要跨不相关的层进行联动修改，且未识别的类型往往会静默丢失。

系统需要支持应用专属的语义卡片类型，同时避免第三方适配器随意注入不可控的 UI 代码或破坏搜索与持久化的稳定性。

## 决策

采用具备版本控制的会话卡片契约，包含以下特性：

1. 卡片的语义 `kind` 由适配器声明并支持扩展。
2. 卡片展现统一使用由 Core 控制的轻量级渲染器注册表（Renderer Registry）。
3. 一个 Part 生成 0 或 1 个 Card；如果包含多张卡片，适配器负责将其拆分为多个 Part。
4. 外部适配器的输出在协议边界处进行一次性结构校验。
5. Core 生成单一的结构化 Card 投影，供 UI、搜索、导出和 Memory 共同消费。
6. 旧版的 `metadata_json.content_card` 通过增量兼容适配器保持支持，直至下游完成迁移。
7. 适配器内容哈希与 Card 契约版本参与 Rehydration 状态计算。
8. 用户派生数据（如翻译、标记）与可替换的解析器输出进行独立存储和保护。
9. 应用专属的类型使用适配器命名空间隔离（例如 `claude-code.reasoning`）；可选的 `semantic_role` 提供跨 App 的通用聚合能力。
10. 卡片的标识符即为稳定的 Part ID，不再包含类型名、渲染器名或旧版后缀。旧版锚点仅作为只读兼容元数据保留。
11. Manifest 声明只允许选择 Core 自有的渲染器，并通过 `allowed_renderers` 显式约束渲染器覆盖。
12. 平台专属的文本解码与噪声清洗职责归属于 Adapter 包内部。Core 与前端不再解析源运行器标签、转义约定或终端包裹层。

## 备选方案

### 继续扩展全局枚举（Global enum）

- 优点：仅增加单个类型时较为简单。
- 缺点：在每个消费方中重复紧耦合，无法支持不同 AI 应用的独立演进。
- 结论：否决。每增加一种类型都会加剧协调成本与静默失配风险。

### 允许适配器提供自定义前端组件

- 优点：具备最大化的渲染灵活性。
- 缺点：引入了任意代码执行风险、版本偏离、样式碎片化以及极大的信任攻击面。
- 结论：否决。适配器仅提供数据和渲染器提示，不提供 UI 代码实现。

### 仅存储不透明元数据并由各消费方自行解释

- 优点：初期无需进行数据迁移。
- 缺点：保留了多个解析器与不一致的语义。
- 结论：否决作为目标架构；仅作为临时的旧版输入格式保留。

### 一次性重构替换整个会话子系统

- 优点：理论上能迅速达成干净的最终架构。
- 缺点：极易破坏现有的适配器、历史记录、翻译、搜索 ID 以及正在进行的 Memory 研发工作。
- 结论：否决。采用在现有模块树内进行增量式的绞杀者迁移（Strangler Migration）。

## 后果

- 新的应用专属语义类型可以直接复用现有的渲染器，无需发布 AssetIWeave 新版本。
- 新增渲染器依然属于受控的 Core 核心特性，具备严格的安全与兼容性准入门禁。
- 命令/结果文本可以随着各源格式的演进而独立发布对应 Adapter 包；Core 保持为与具体源无关的协议、持久化和投影层。
- Core 增加了卡片校验/投影模块，并成为通用搜索/导出语义的权威所有者。
- Card Contract v1 导入只生成结构化的 Card 描述符；Core 针对历史数据库和旧适配器临时保留对旧版元数据的双读能力。
- 聚合的同步/导出操作日志提供了持续两个发版周期、零使用记录的废弃凭证，而无需记录单个 Part 日志。
- 搜索和前端类型 API 从固定枚举拓宽为经过校验的动态标识符。
- 深度链接统一使用稳定的 Part/Card ID，同时保持对旧版 `${part_id}-${type}` 锚点的解析兼容。
- 解析器刷新逻辑必须完整保留翻译等用户派生数据。
- 尽管此次迁移的工作量大于简单增加一个枚举项，但彻底消除了长期的跨层协同维护成本。

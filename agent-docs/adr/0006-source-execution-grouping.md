# 0006: 保留源执行标识以支持会话分组

> 状态：已部分取代
> 决策日期：2026-08-03
> 决策证据：`a58215f`
> 记录日期：2026-08-03

## 背景

会话适配器此前将命令及其执行结果规范化为相互独立的 Part 和 Card。它们在数组中的顺序并不是可靠的配对机制，因为多个工具调用可能会交错发生；而通过命令文本、时间戳或相邻关系来重建关联又会引入启发式规则和误匹配。

Codex、Claude Code 和 OpenCode 已经在其源记录中提供了稳定的调用标识符（call identifier）。Antigravity Updater 暂未暴露同等可靠的标识符。UI 应当将命令及其执行结果作为一个父子 Execution 单元进行展示，而无需在前端重建内存查找表或维护特定源的匹配规则。

## 决策

1. 在规范化和持久化的会话 Part 中增加可为空的 `source_execution_id` 字段。
2. Codex、Claude Code 和 OpenCode 适配器直接复制源调用标识符，不进行重写或语义校验。Antigravity 将该字段置为空（null）。
3. 不增加独立的 Execution 实体或关系表。Execution 是基于 Part 的只读投影，不是独立可变的数据模型。
4. Rust Core 仅对语义角色为 `command` 或 `result` 且其 Part 共享相同 `(turn_id, source_execution_id)` 二元组的 Card 进行分组。
5. Question 详情响应保留原有的扁平 `cards` 数组，并增加有序的 `content_nodes` 结构。Execution 节点通过数组索引引用 command/result Card，避免 Card 正文的冗余复制。
6. 前端直接消费 `content_nodes` 进行渲染，不再进行任何 ID 匹配。未包含结构化节点的旧记录保留原有的扁平 Card 渲染路径。
7. 首张 Card 的出现位置决定 Execution 节点在时间线中的位置。节点内部的 Result 顺序依然沿用源 Part 的顺序。

## 备选方案

### 增加 Execution 表或关系映射表

- 优点：提供了一等公民的持久化关系。
- 缺点：为了完全可以从导入记录中准确派生的数据，增加了 Schema 生命周期、写入同步和数据清理的工作量。
- 结论：否决。源标识符加上 Part 的归属关系已经足够充分，且比维护第二份可变表示更加稳定。

### 在前端匹配命令与结果

- 优点：无需改动后端 DTO。
- 缺点：在展示层重复领域逻辑，增加每次渲染的内存分配，并导致非 UI 消费方的行为不一致。
- 结论：否决。Core 拥有对规范化会话投影的权威控制权。

### 按顺序、命令文本或时间戳进行启发式匹配

- 优点：可以覆盖没有调用标识符的源。
- 缺点：对于交错执行或重复的命令会产生歧义和错误匹配。
- 结论：否决。没有可靠标识符的源保持扁平展示，直至其适配器能够提供标识符为止。

### 在 Rust 中二次确认源 ID 的有效性

- 优点：可以拒绝格式不良的适配器输出。
- 缺点：如果不引入特定源的启发式规则，无法实质改善权威的不透明标识符。
- 结论：否决。协议形态校验留在适配器边界；分组仅使用完全相等的匹配。

## 后果

- 即使执行结果无序到达，Command/Result 的分组也是确定性的。
- 持久化层增加了一个可空的源标识字段，而 Execution 保持为可替换的只读模型。
- 前端内存占用与返回的节点/索引数组保持线性比例，无需额外的配对 Map。
- 扁平的 Card 数组继续可用于搜索、导出、深度链接及向下兼容。
- `content_nodes` 索引仅在同一个 Question 详情响应的 `cards` 数组内有效，消费方严禁持久化该索引。
- Antigravity 会话保持非分组状态，而非进行投机性的猜测匹配。

# AssetIWeave 后端架构统一收口

## 1. 背景

AssetIWeave 后端目前已经形成了一批新的稳定基础设施：

```text
AppRuntime
AppService
TaskRuntime
AgentExecutionRuntime
AppError
HostProcess
HostFilesystem
Conversation Adapter Catalog v2
Capabilities
Domain Event / Outbox
```

整体方向已经比较清晰：

```text
Transport / Adapter
        ↓
Application
        ↓
Domain / Runtime / Capability
        ↓
Infrastructure
```

但当前代码仍处于架构迁移期，部分旧执行路径没有完全退出，形成多个  **Authority Duplication / Migration Seam** 。

典型情况包括：

```text
TaskRuntime
+
BackgroundTaskRegistry

AppError
+
Result<T, String>

AppRuntime Catalog
+
DB fallback

AgentExecutionRuntime
+
legacy_gemini

Catalog v2
+
Legacy Script Catalog Installer

HostProcess / HostFilesystem
+
Application 直接调用 std::process / std::fs
```

这些问题的核心并非代码重复本身，而是：

> **同一个后端概念存在两个具有实际行为或状态所有权的实现路径。**

长期会导致新功能不知道应该进入哪条路径，AI Agent 也容易复制 Legacy 实现，使已经开始收口的架构再次分叉。

---

# 2. 目标

本次重构目标：

> **为 AssetIWeave 后端的重要基础能力确定唯一 Canonical Path，并逐步移除 Legacy Authority。**

目标架构：

```text
                   Tauri / CLI / Engine
                           │
                           ▼
                   Transport Adapter
                           │
                           ▼
                      AppService
                    Application Layer
                           │
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
     Capabilities      TaskRuntime    AgentExecutionRuntime
          │                │                │
          ▼                ▼                ▼
        Store          Task Kernel      Agent Backends
          │                                  │
          ▼                             ACP / CLI / ...
        SQLx


Cross-cutting Infrastructure

AppRuntime
AppError
HostFilesystem
HostProcess
DomainEvent / Outbox
Extension Kernel
```

核心原则：

```text
一个概念
    ↓
一个 Authority
    ↓
多个 Adapter / Projection
```

允许存在 Compatibility Adapter，但不允许 Compatibility Layer 成为第二个事实源。

---

# 3. 非目标

本阶段不进行以下工作：

* 不全面重写后端。
* 不替换 SQLx。
* 不为了形式统一把所有模块改成 Trait。
* 不把所有业务行为都 Event Sourcing 化。
* 不强制所有普通 `std::fs` 调用经过 HostFilesystem。
* 不重构所有大型 Rust 文件。
* 不修改现有 IPC API，除非为架构收口确有必要。
* 不一次性删除所有 Legacy compatibility code。
* 不强制 `capabilities` 立即成为唯一 Domain Layer。
* 不重新设计 Conversation Adapter 协议。

重点是：

> **消除双 Authority，而不是追求抽象数量。**

---

# 4. P0：TaskRuntime 成为后台任务唯一生命周期事实源

## 4.1 当前问题

后端已经存在：

```text
runtime/tasks.rs
    ↓
TaskRuntime
```

统一定义：

```text
TaskKind
TaskSpec
TaskState
TaskSnapshot
cancel
progress
deduplication
shutdown
```

但 Tauri adapter 中仍存在：

```text
BackgroundTaskRegistry
```

维护 ConversationSync、Memory、Backup、AI Execution、Agent Lifecycle、Search Index 等领域任务状态。

因此形成：

```text
             TaskRuntime
            /           \
      execution         lifecycle

BackgroundTaskRegistry
      ↓
另一套 task state / projection
```

如果 Registry 同时负责状态转换、取消判断、running 判断或 terminal 状态，就形成第二 Authority。

---

## 4.2 目标

最终：

```text
TaskRuntime
    │
    │ canonical lifecycle
    ▼
TaskSnapshot
    │
    ├── ConversationSyncProjection
    ├── MemoryTaskProjection
    ├── AiExecutionProjection
    └── BackupProjection
            │
            ▼
       Tauri Event DTO
```

明确：

```text
TaskRuntime
=
任务生命周期唯一 Authority

Domain Projection
=
TaskRuntime 状态的领域化展示

Tauri Registry
=
不得拥有独立生命周期
```

---

## 4.3 实施要求

保留领域 Snapshot，例如：

```rust
ConversationSyncTaskSnapshot
AiExecutionTaskSnapshot
MemoryTaskSnapshot
```

但其核心状态：

```text
queued
running
succeeded
failed
cancelled
```

必须来源于 TaskRuntime。

逐步移除 `BackgroundTaskRegistry` 中以下职责：

```text
running ownership
terminal lifecycle
cancel authority
task existence authority
task cleanup authority
```

允许保留：

```text
domain-specific result
progress projection
UI-facing aggregation
event payload construction
```

---

## 4.4 验收

必须满足：

```text
同一个 task id 的生命周期只由 TaskRuntime 决定。

TaskRuntime 删除 task 后，
Registry 不得仍认为 task running。

取消操作必须首先进入 TaskRuntime。

新增 TaskKind 不需要复制完整 lifecycle registry。
```

并增加架构测试，阻止新的独立 lifecycle registry 出现。

---

# 5. P0：统一 AppError，逐步退出 `Result<T, String>`

## 5.1 当前问题

已经存在：

```rust
AppError
AppErrorView
```

并包含：

```text
Validation
NotFound
Conflict
Io
Db
Extension
Canceled
Legacy
```

但 Application Layer 仍广泛使用：

```rust
type AppResult<T> = Result<T, String>;
```

形成：

```text
旧路径：

Application
    ↓
String


新路径：

Runtime / Infrastructure
    ↓
AppError
    ↓
AppErrorView
```

---

# 5.2 目标

统一为：

```text
Domain / Infrastructure
        ↓
     AppError
        ↓
   Application
        ↓
Transport Adapter
        ↓
   AppErrorView
```

规则：

```text
AppError
=
内部错误类型

AppErrorView
=
IPC / 用户展示 DTO

String
=
错误 message，而不是错误类型
```

---

## 5.3 实施步骤

推荐渐进迁移：

```rust
pub type AppResult<T> = Result<T, AppError>;
```

优先迁移：

```text
AppService
TaskRuntime
AgentExecutionRuntime
Conversation Adapter
Capabilities
Store-facing Application logic
```

Transport 层统一：

```rust
AppError -> AppErrorView
```

不要在 Application 中重复：

```rust
.map_err(|error| error.to_string())
```

---

## 5.4 Legacy

`AppError::Legacy(String)` 可以暂时保留作为迁移桥：

```text
Legacy module
    ↓
String
    ↓
AppError::Legacy
```

但禁止：

```text
AppError
    ↓
String
    ↓
Application
```

即新架构不能反向降级。

最终可以在 Legacy Path 退出后删除：

```rust
AppError::Legacy
```

---

# 6. P0/P1：AgentExecutionRuntime 成为 Agent 执行唯一入口

## 6.1 当前问题

当前已经有：

```text
AgentExecutionRuntime
```

OpenCode translation 已进入统一 Agent Runtime。

但 Gemini 仍存在：

```text
legacy_gemini
```

并由 translation / connection-test 直接调用。

因此：

```text
OpenCode
    ↓
AgentExecutionRuntime


Gemini
    ↓
legacy_gemini
    ↓
CLI
```

---

# 6.2 目标

Application 不再区分：

```text
OpenCode execution
Gemini execution
Future Agent execution
```

而只表达：

```text
AgentId
ActionId
ExecutionRequest
```

例如：

```text
Translation
    ↓
AgentExecutionRuntime
    ↓
resolve Agent Backend
    ├── OpenCode
    ├── Gemini
    ├── ACP
    └── Future Agent
```

---

## 6.3 目标接口

概念上：

```rust
AgentExecutionRuntime::execute(
    AgentExecutionRequest {
        agent_id,
        action,
        model,
        prompt,
        ...
    }
)
```

具体 Gemini CLI invocation 应进入：

```text
Agent Backend / Adapter
```

而不是存在于：

```text
card_translation
AppService
Tauri command
```

---

## 6.4 验收

代码中不应再出现：

```text
if agent == gemini {
    legacy_gemini...
}
```

Application 不应知道 Gemini 的进程启动参数。

Translation / Connection Test 均走同一 Agent Runtime。

新增 Agent 不需要修改 Translation 核心逻辑。

---

# 7. P1：移除 `AppService runtime: Option` Production/Legacy 双入口

## 7.1 当前问题

`AppService` 当前允许：

```rust
runtime: Option<Arc<AppRuntime>>
```

主要用于旧测试构造方式。

导致业务代码出现：

```rust
if let Some(runtime) = self.runtime {
    ...
} else {
    // DB fallback
}
```

于是：

```text
Production
    ↓
AppRuntime Catalog


Legacy Test
    ↓
DB Query
```

同一个业务概念存在两个 authority path。

---

# 7.2 目标

正式结构：

```rust
pub struct AppService {
    runtime: Arc<AppRuntime>,
}
```

即：

```text
AppRuntime
永远存在
```

测试也进入正式架构：

```text
Test AppRuntime
    ├── Temp DB
    ├── Fake HostProcess
    ├── Fake AgentBackend
    └── Test Catalog
```

而不是：

```text
Production Architecture
为旧测试增加 bypass
```

---

## 7.3 实施原则

先迁测试。

不要直接删除 `Option` 后大量 mock 崩溃。

推荐：

```text
建立 TestRuntimeBuilder
        ↓
迁移旧 AppService tests
        ↓
删除 legacy constructor
        ↓
runtime: Arc<AppRuntime>
```

---

# 8. P1：Catalog v2 与 Legacy Script Catalog 共享 Package Installer

## 8.1 当前问题

当前：

```text
Catalog v2 Release
        ↓
转换
        ↓
ConversationScriptCatalogItem
        ↓
Legacy Installer
```

这说明：

```text
Catalog Model
+
Installer Model
```

尚未真正分离。

---

# 8.2 目标

提取一个与 Catalog 版本无关的安装模型：

```rust
ConversationAdapterPackageInstallSpec
```

例如：

```text
id
version
artifact
checksum
runtime
entrypoint
compatibility
...
```

架构：

```text
Legacy Catalog ───────┐
                      │
Catalog v2 ───────────┼─→ InstallSpec
                      │
Local Package ────────┘
                           ↓
                    PackageInstaller
```

最终：

```text
Catalog
负责发现 / metadata

Installer
负责安装
```

---

## 8.3 注意

本阶段不强制删除 Legacy Catalog。

允许：

```text
Legacy Catalog
    ↓
Compatibility Mapper
    ↓
InstallSpec
```

但禁止：

```text
Catalog v2
    ↓
必须转 Legacy Catalog Model
    ↓
才能安装
```

# 9. P1/P2：收紧 HostProcess / HostFilesystem 边界

## 9.1 当前问题

已经建立：

```text
HostProcess
HostFilesystem
```

用于统一：

```text
process spawning
PATH lookup
timeout
termination
cross-platform path
symlink
path normalization
containment
```

但 Application 仍能直接：

```rust
use std::{
    env,
    fs,
    process::Command,
};
```

因此平台敏感能力仍可能绕过 Host abstraction。

---

# 9.2 目标

不禁止普通标准库调用。

只限制  **platform-sensitive capability** 。

必须经过 HostProcess：

```text
启动外部进程
寻找 executable
shell resolution
timeout
kill / terminate
process tree
```

必须经过 HostFilesystem：

```text
symlink
cross-platform path normalization
portable path validation
path equality
containment/security-sensitive path checking
```

普通：

```rust
fs::read_to_string()
fs::write()
```

如果不存在特殊平台语义，不必强行封装。

---

# 9.3 Architecture Guard

建议增加边界检查：

```text
application/
不得直接 std::process::Command
```

对于 `std::fs` 不建议全面禁止。

可以针对危险 API 建 allowlist / denylist。

---

# 10. P2：明确 Capabilities 的 Architectural Contract

当前：

```text
capabilities/catalog
capabilities/groups
capabilities/mounts
capabilities/profiles
capabilities/sources
```

已经出现。

但目前它到底是：

```text
A. 可复用业务函数集合
```

还是：

```text
B. AppService 与 Store/Infrastructure 之间的正式 Domain Capability Layer
```

还不完全清晰。

本阶段不强制重构。

需要先在文档中明确。

推荐定义：

> `capabilities` 表示跨多个 repository / infrastructure operation 的稳定领域能力；简单 CRUD 不需要为了分层而进入 capability。

因此：

```text
复杂业务 transaction
→ capability

单表 CRUD
→ store

workflow orchestration
→ AppService
```

避免未来演变成：

```text
AppService
↓
Capability
↓
Store
```

所有代码无意义地机械套三层。

---

# 11. Database Backup 特殊路径

`data_backup` 目前存在：

```text
独立 Tokio Runtime
独立 SqlitePool
VACUUM / checkpoint
filesystem copy
```

本阶段不统一到 Resident AppRuntime。

原因：

```text
backup during shutdown
```

可能天然需要独立 lifecycle。

需要做的是明确标记：

```text
OneShot / Shutdown Infrastructure Path
```

并注明：

> 此模式是数据库关闭/恢复基础设施特例，不是普通 Application Service 的推荐实现。

防止以后复制：

```text
new Tokio runtime
+
open another DB pool
```

处理普通业务。

---

# 12. Architecture Guard

这次后端收口应像前端一样，不只改代码，还要建立 executable architecture rules。

推荐加入：

```text
backend architecture boundaries

1. Application 默认使用 AppError，不新增 Result<T, String>
2. Tauri command 不直接执行 Agent CLI
3. Agent execution 必须经过 AgentExecutionRuntime
4. 新 Background Task 必须注册进入 TaskRuntime
5. Application 不得直接使用 std::process::Command
6. Production AppService 必须由 AppRuntime 构建
```

短期可以通过：

```text
Rust test
grep-based source guard
现有 module-boundary script
```

实现。

长期规则增多后，再考虑：

```text
clippy custom lint
cargo-deny style checker
AST-based architecture checker
```

不需要本阶段引入复杂工具。

---

# 13. 推荐实施顺序

```text
Phase 1
TaskRuntime Single Authority
        ↓

Phase 2
AppError 全链路迁移
        ↓

Phase 3
AgentExecutionRuntime
移除 legacy_gemini execution path
        ↓

Phase 4
AppService / AppRuntime 单入口
        ↓

Phase 5
Catalog-independent PackageInstaller
        ↓

Phase 6
HostProcess / HostFilesystem boundary
        ↓

Phase 7
Capabilities contract documentation
        ↓

Phase 8
删除残余 Legacy compatibility path
```

不要一次并行做全部。

前三阶段属于最优先架构工作。

---

# 14. 验收标准

第一阶段完成后，至少满足：

* `TaskRuntime` 是任务生命周期唯一事实源。
* 不再新增独立 `BackgroundTaskRegistry` lifecycle logic。
* Application 新代码统一返回 `AppError`。
* `Result<T, String>` 只允许在明确 Legacy boundary 中存在。
* Translation / Connection Test 不直接调用 `legacy_gemini`。
* Gemini 进入 `AgentExecutionRuntime` backend。
* Production `AppService` 必须具有 `AppRuntime`。
* Catalog v2 不依赖 Legacy Catalog model 才能安装 package。
* 平台敏感 process 操作经过 `HostProcess`。
* Modal 前端类似的 architecture guard 思路同步应用到 Rust 后端。
* 所有 Legacy compatibility path 都必须有明确注释和退出计划。

---

# 15. 最终原则

这次后端重构的核心不是增加更多层，而是：

```text
Stable Core
    ↓
唯一事实源

Variable Capability
    ↓
Adapter / Projection
```

具体对应：

```text
TaskRuntime
=
Task Lifecycle Core

AgentExecutionRuntime
=
Agent Execution Core

AppRuntime
=
Process Runtime Core

AppError
=
Error Core

HostProcess / HostFilesystem
=
OS Boundary

PackageInstaller
=
Adapter Installation Core
```

Legacy 模块可以暂时继续存在，但必须逐步变成：

```text
Legacy
   ↓
Compatibility Adapter
   ↓
Canonical Core
```

而不能继续是：

```text
Canonical Core
        +
Legacy Core
```

并行运行。

**最终目标不是“后端所有代码风格一致”，而是让每一种基础能力都只有一个明确的 Authority。**

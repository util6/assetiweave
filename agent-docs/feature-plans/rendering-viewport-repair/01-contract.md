# 渲染视口与快速滚动缺口修复契约

## Problem Statement

用户在浏览长 Conversation Question 和 Skill 资产列表时，快速拖动滚动条或快速返回已浏览区域会看到短暂空白、背景穿透或内容来不及出现。现有实现虽然已经具备虚拟化、Overscan、Skeleton 和延迟复杂内容提交，但 Conversation 预览没有从应用可用高度一直传递到内部滚动元素的完整约束链，导致虚拟化收到数万像素高的“视口”。当视口被正确限制后，虚拟窗口仍以异步方式跟随滚动位置，造成滚动位置已经变化而新虚拟行尚未提交的帧级覆盖缺口。

Skill 资产列表属于另一条问题链：它直接挂载全部资产，没有使用 Conversation 的虚拟窗口；同时长列表整体和每行操作区重复使用背景模糊，使 WebKit 在长滚动表面上承担不必要的绘制与合成成本。现有测试主要固定模拟一个 240px 视口或检查 CSS 字符串，无法证明真实布局、逐帧 DOM 覆盖和原生 WebKit 像素输出正确。

## Solution

应用应先建立唯一、稳定的可用高度来源，将有界高度通过 Conversation Workspace、分栏容器、预览根节点、固定标题区和内部滚动区逐层传递；虚拟列表必须以该内部滚动区的真实 `clientHeight` 计算挂载范围。滚动位置变化时，轻量虚拟行壳和 Skeleton 必须同步提交，复杂 Markdown、Diff、工具结果仍由既有调度器延迟恢复。

Skill 资产列表应先移除长列表整体和重复行操作区的背景模糊，并建立明确的内部滚动归属。完成原生 WebKit 采样后，只有达到数据规模或性能门禁时才接入列表虚拟化，避免在根因未分离前同时引入多个变量。

验收必须沿同一条真实用户路径记录 DOM 覆盖、几何位置和原生像素结果：向下浏览多段内容，快速返回已浏览区域，再连续往返。最终标准是画面无缺口，而不是 CSS 已修改或单元测试已通过。

## User Stories

1. 作为浏览长 Conversation Session 的用户，我希望 Question 预览始终拥有稳定的可视高度，以便长内容不会撑开整个工作区。
2. 作为浏览长 Conversation Session 的用户，我希望问题列表展开时预览仍在自己的滚动区域内滚动，以便左右分栏互不争夺页面滚动。
3. 作为浏览长 Conversation Session 的用户，我希望问题列表收起时预览继续使用同一个有界滚动模型，以便布局切换不会重新引入整页膨胀。
4. 作为快速拖动滚动条的用户，我希望滚动到任意位置的第一帧都有真实内容或 Skeleton 覆盖，以便不会看到背景空洞。
5. 作为向上返回已浏览内容的用户，我希望虚拟化能及时重新挂载已卸载的 Turn，以便“浏览过”与“当前可见”之间没有显示断层。
6. 作为逐步向下阅读的用户，我希望现有渐进展示与复杂内容延迟渲染继续生效，以便修复不会恢复一次性挂载全部复杂内容。
7. 作为搜索 Conversation 内容的用户，我希望屏幕外命中仍能定位到正确 Turn 和 Card，以便虚拟化修复不破坏搜索导航。
8. 作为调整 Conversation 分栏宽度的用户，我希望预览重新测量后仍保持正确滚动位置和行高度，以便不会产生明显跳动。
9. 作为展开 Result 或 Diff 的用户，我希望展开状态在虚拟行卸载与重新挂载后保持，以便滚动优化不丢失交互状态。
10. 作为执行翻译或复制操作的用户，我希望后台任务和反馈状态不因虚拟行卸载而重复、取消或丢失。
11. 作为使用键盘浏览的用户，我希望 PageUp、PageDown、Home 和 End 与指针滚动具有相同的无空白保证。
12. 作为使用浅色或深色主题的用户，我希望快速滚动时都不会看到窗口底色穿透。
13. 作为启用 reduced motion 的用户，我希望修复不依赖动画并继续遵守现有 Skeleton 动效策略。
14. 作为浏览 Skill 资产的用户，我希望 130 条资产快速滚动时列表持续可见，以便管理工作不被绘制缺口打断。
15. 作为拥有 1,000 条 Skill 资产的用户，我希望挂载量与视口范围相关，以便列表规模增长不会线性放大 DOM 和绘制成本。
16. 作为操作 Skill 资产的用户，我希望展开、快速挂载、编辑、删除、路径定位和分组信息继续正确工作。
17. 作为筛选和排序 Skill 资产的用户，我希望列表变化后稳定资产身份、滚动几何和展开状态保持正确。
18. 作为切换列表/网格视图的用户，我希望滚动容器和视觉表面不会产生双滚动条或丢失当前位置之外的业务数据。
19. 作为维护者，我希望能区分“没有 DOM”“DOM 几何错误”和“DOM 正确但 WebKit 未绘制”三种故障，以便后续补丁针对真实层级。
20. 作为维护者，我希望自动化测试使用真实组件链路而不是只检查类名，以便布局失控能在合入前被发现。
21. 作为维护者，我希望每个修复阶段有独立基线和提交，以便回归时可以准确定位变量。
22. 作为维护者，我希望公共虚拟化组件默认保证行壳同步覆盖，而复杂内容继续异步，以便性能与画面完整性分层处理。
23. 作为维护者，我希望原生 WebKit 验收使用确定性压力数据和固定操作协议，以便不同实现之间可以比较。
24. 作为维护者，我希望修复不更改 Conversation 或 Asset 的领域数据契约，以便前端渲染修复不扩散到后端。

## Implementation Decisions

- 应用内容区域必须提供明确的视口可用高度；最小高度只用于下限，不能作为虚拟化视口契约。
- Conversation Workspace 在问题列表展开和收起两种分支中都必须占满可用高度并允许后代收缩。
- 分栏画布、面板和预览根节点必须连续传递 `height: 100%` 与 `min-height: 0` 语义；任一中间层不得由长内容反向撑高。
- QuestionPreview 的标题区是不可收缩区域，内容区是唯一纵向滚动所有者；外层页面不得与其形成竞争性的嵌套纵向滚动。
- 正式实现使用窗口剩余空间或应用内容区高度，不写死调查实验中的 600px。
- VirtualizedCollection 必须启用同步范围提交；同步范围只覆盖虚拟行壳、定位 wrapper 和 Skeleton 边界。
- 复杂 Markdown、Diff、代码、工具结果和其他重型子树继续由现有 Deferred Skeleton 与 Render Scheduler 控制，禁止因同步范围提交而全部同步渲染。
- 不通过增加 Overscan、初始渲染数量或 Skeleton 数量替代有界视口和同步范围提交。
- Skill 资产列表先执行绘制减负：移除长列表整体和每行操作区的背景模糊，使用既有语义 Theme Token、渐变、边框和阴影保持层次。
- 玻璃效果仅允许保留在尺寸有限的固定工具栏或弹出层，不能覆盖数万像素高的滚动表面。
- Skill 资产列表必须有明确的内部滚动元素；PageHeader 和 AssetToolbar 留在滚动区域之外，列表/网格内容共享同一滚动归属，避免双滚动条。
- Skill 列表虚拟化是条件阶段：当原生采样仍有绘制缺口、130 条出现超过 50ms 的滚动长任务，或 1,000 条挂载量与总数线性增长时执行。
- 若接入 Skill 列表虚拟化，以 Asset ID 为稳定 key，展开状态继续由列表外部控制；挂载、编辑、删除等操作不得依赖当前 DOM 全量存在。
- 所有诊断采用同一分类：无行覆盖属于虚拟范围提交问题；行框位置或尺寸错误属于测量/锚点问题；DOM 与几何正确但画面空白属于 WebKit 绘制/合成问题。
- 本修复补充 ADR-0010 的前置不变量，不推翻统一渲染架构。
- 不涉及数据库迁移、Tauri 命令、Engine 协议或新生产依赖。

## Testing Decisions

- 最高测试缝是使用真实 SessionQuestionWorkspace、QuestionPreview、ResizableColumns、RenderSafeScrollSurface 和 VirtualizedCollection 组合的压力路径；不以单个 CSS 类测试替代组合行为。
- Conversation 布局测试必须覆盖问题列表展开和收起两种分支，并验证内部滚动元素具有有限、非零、稳定的高度，内容总高度增长不会改变视口高度。
- VirtualizedCollection 行为测试必须模拟大跨度向下和向上跳转，逐帧计算虚拟行区间对 `[scrollTop, scrollTop + clientHeight]` 的并集覆盖；每帧覆盖率必须为 100%。
- 保留现有 80 Turn 确定性压力夹具，并增加能记录 viewport height、scrollHeight、mounted item count、row interval 和 frame coverage 的诊断能力。
- Skill 列表使用 130 条和 1,000 条确定性 Asset fixture；测试外部行为包括滚动、展开、筛选、排序、编辑/删除触发和挂载操作，不检查内部 state 形状。
- CSS 测试只作为防止背景模糊回归的辅助门禁；最终画面结果由 Tauri macOS WebKit 验收。
- 原生验收必须同时记录 DOM、几何和屏幕画面，避免仅凭截图推断根因。
- 所有测试使用稳定数据和固定窗口条件，不使用随机 ID、随机高度或未记录的人工数据。
- 既有 Conversation 与 Catalog 回归测试、TypeScript strict、Vitest 全量测试和生产构建均为必需门禁。

## Out of Scope

- 重写统一 Skeleton、Render Scheduler 或 Conversation Card renderer。
- 调整 Conversation 的数据加载分页、命令投影上限或后端同步策略。
- 将“浏览过的数据”永久保留为 DOM。
- 为 Markdown、Diff、代码、图片或工具结果分别实现独立虚拟化算法。
- 持久化精确 Turn/Asset 行高到 SQLite 或本地设置。
- 一次性推广到 Source、Group、Mount、Memory 或其他所有长列表。
- 使用 Canvas、截图缓存、WebGL 或位图快照替代 React 内容。
- 在没有独立证据时加入 GPU 强制分层、任意 `will-change`、额外 containment 或无限增加 Overscan。
- 修改产品视觉语言、资产领域模型或 Conversation 语义投影契约。

## Further Notes

- 已确认的对照数据：原布局下 Conversation 内部滚动视口约 36,343px 且挂载 80 Turn；修正高度链后约 469px 且挂载 4 Turn。在一个明确 600px 的实验父容器中，仅补齐 QuestionPreview 的完整高度语义后，内部视口约 503px、挂载 4 Turn。
- 已确认的提交时序数据：修正高度后，16 次大跨度跳转、每次采样 3 帧，共 48 帧；异步范围提交出现 15 帧无虚拟行覆盖，同步范围提交为 0，重复实验仍为 0。
- Skill 资产列表的调查数据：130 条时列表约 16,597px，高度链上存在 131 个背景模糊元素，全部 130 行同时挂载。这证明绘制风险存在，但尚未单独证明背景模糊是原生截图缺口的唯一根因。
- 现有 9 个渲染相关测试文件、22 个测试通过，只能说明当前测试覆盖不足，不能作为问题不存在的证据。

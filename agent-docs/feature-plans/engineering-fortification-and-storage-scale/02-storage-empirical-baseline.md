## 0. 一句话结论（先说结果）

**三个"免费"的清理动作能在不改一行代码的情况下把 `~/.assetiweave` 从 48.3 GiB 降到约 13.2 GiB（-73%）：**

| 动作 | 回收 | 前置条件 |
|---|---:|---|
| ① `VACUUM` 主库（77.5% 是空闲页） | **1.24 GiB** | 无，纯 SQLite |
| ② 删除 81 个废弃的 Tantivy `.tmp` 索引代数 | **22.68 GiB** | 无，索引本身只有 0.32 GiB 有效 |
| ③ 清理 7 个 `app.db.bak_*` 全量备份 | **11.21 GiB** | 需确认无回滚需求 |

**而"Zstd 压缩 + 去重"整套工程，在主库上最多再省 205 MiB（370 MiB → ~177 MiB，块级模型全量实测 5.241x）；若用逐行模型只有 163 MiB。**
真正的大头不是正文，是索引目录的泄漏（占 48.3 GiB 的 51%）和主库的碎片（主库自身 77.5% 是空的）。

换句话说：**「先治索引膨胀/清备份，再谈压缩去重」是对的，而且前者工作量近乎为零、收益是后者的 12 倍。**

## A. 主库真实体积结构

### A.1 页级物理事实

| 指标 | 值 |
|---|---|
| `journal_mode` | `wal` |
| `auto_vacuum` | `0`（**关闭**，故 `PRAGMA incremental_vacuum` 是空操作） |
| `page_size` | 4,096 B |
| `page_count` | 420,063 |
| 文件大小 | 1,720,578,048 B = **1.602 GiB** |
| `freelist_count` | **325,384 页** = 1,332,772,864 B = **1.241 GiB** |
| **空闲页占比** | **77.47%** |
| 实际在用页 | 94,678 页 = 387,801,088 B = **369.9 MiB（22.53%）** |
| 有效 cell payload | 336,857,120 B = 321.3 MiB |
| 页内未用空间（`unused`） | 46,657,603 B = 44.5 MiB |
| 页内空间利用率 | 336.9 / 387.8 = **86.9%** |
| `-wal` | 36,824,592 B = 35.1 MiB |

**结论：主库是一具 1.6 GiB 的空壳。** 真实数据只有 370 MiB，其余 1.24 GiB 是历史 DELETE 留下的 freelist 页。

> **附带发现：11.21 GiB 无人认领的裸副本**（已与路径侧交叉核对，结论如下）
>
> `~/.assetiweave/` 下有 **7 个**主库副本，**字节数全部精确等于 1,720,578,048 B —— 与主库一模一样，一个字节都不差**：
> `app.db.bak_1793541197` / `bak_data_clean_1793841520` / `bak_data_clean_1793841964` / `bak_pathfix_20261108_181713` / `bak_cwdfix_20261108_192137` / `bak_compact_20261115_103243` / `bak_compact_20261115_111731`（合计 **11.21 GiB**）。
>
> 其中两个名为 `bak_compact_*`（2026-11-15 11:10 与 11:17，间隔 7 分钟）——**已经有人跑过两次"压缩"，产物与源库同尺寸、主库 freelist 依旧 1.24 GiB。**
>
> **归属判定（两人独立核对代码后，结论分两层）**
>
> **第一层：这 7 个文件不是本仓代码产出的。**
> App 备份产物命名格式是 `assetiweave-app-<YYYYMMDD-HHMMSS-mmm>-<uuid8>.db`（`infrastructure/backup/mod.rs:202-206` 的 `backup_file_name()`），而 `~/.assetiweave/` 下**没有任何** `assetiweave-app-*.db`；那 7 个文件名全部不符合该格式，仓库里也 grep 不到 `bak_compact|bak_data_clean|bak_pathfix|bak_cwdfix` 任何字面量。
> → 它们是**外部 `cp` 或手写修复脚本**留下的，不受任何清理逻辑管辖。**"compact 功能从未生效"这个结论对 Rust 路径不成立，撤回。**
>
> **第二层：但"产物与源库逐字节相同"这个观测，在 App 里是可复现的——因为它有一条静默降级通道。**
> `vacuum_into`（`mod.rs:179-188`）用 `Connection::open_with_flags(READ_WRITE|NO_MUTEX)` 直接 `VACUUM main INTO ?1`。**更正一条我最初写错的：rusqlite 默认 `busy_timeout` 不是 0。** 实测 `rusqlite-0.37.0/src/inner_connection.rs:119` 在每次 open 时都会 `sqlite3_busy_timeout(db, 5000)` ⇒ 默认 **5000 ms**。所以正确表述是「**锁等待超过 5 秒才失败**」，触发概率不高、但不为零（长导入/长写事务期间仍可能撞上）。
> 失败后 `or_else` 落到 `checkpoint_and_copy`（`mod.rs:190-200`）= `wal_checkpoint(TRUNCATE)` + **`fs::copy`** → **产物与源库逐字节同级**，与本报告观察到的现象完全一致；
> 且降级**全程静默**：`or_else` 丢弃 `vacuum_error`；`verify_sqlite_snapshot`（`mod.rs:128-141`）只跑 `PRAGMA quick_check`，它只验结构一致性、不看空间，含 1.24 GiB 空洞的胖副本照样返回 ok；上层拿到 `Ok(BackupTarget)`，**无法区分"真压缩"与"纯拷贝"**。
>
> **定性：这是「可观测性缺口」（低严重度），不是高频 bug。** 正常路径下 App 备份是正确的（`VACUUM INTO` 重建库）。它的真正危害不在"经常失败"，而在**失败时用户和代码都无法察觉**——压缩方案上线后，用户跑一次备份、看到磁盘没变，就会判定"压缩无效"，而日志里什么都没有。
>
> → 因此那两次 `bak_compact_*` 的可能链路是：**外部脚本调用 App 的导出路径 → 撞锁超 5 s 静默降级为 `fs::copy` → 脚本把产物重命名为 `bak_compact_*`**。7 分钟内的第二次尝试，也符合"第一次看着没效果、再试一次"的行为。**⚠️ 此为推测（未验证）**：既没有看到那个脚本，也没有 App 产物残留可供反推，**不要当事实引用**。
> **对外表述应该用"备份在降级时会静默产出与源库等大的副本、且无任何告警"，而不是"压缩从来没生效"——前者是可观测性缺口，后者是被证伪的指控。**
>
> **对本报告结论的影响（不撤回任何数字）：**
> 1. **11.21 GiB 是"压缩前时代"的遗留明文，App 不知道它们存在，压缩上线后也不会变小。** 必须单独出孤儿清理策略（判据：文件名不在 App 命名白名单 + 尺寸等于某代主库 → 列为孤儿）。
> 2. 静默降级通道是 **低严重度的可观测性缺口（附带项，随手做）**，不是高频 bug：`or_else` 加 `tracing::warn!` 并把降级标记回填、产物断言 `freelist_count≈0`（或 `page_count` 未变即报错）、`quick_check` 升级为"尺寸 + freelist"双校验。**不需要改 `busy_timeout`——默认 5000 ms 已经够用。**
> 3. `auto_vacuum` 实测为 `0`（未设），即便调 `PRAGMA incremental_vacuum` 也是空操作——这是 1.24 GiB 碎片**会复发**的机制性原因，与上面 7 个裸副本是两件独立的事。

### A.7 按页类型拆分：35.8% 的在用空间是溢出页（压缩的真实靶子）

`dbstat` 的 `pagetype` 列（全库 94,678 页）：

| 页类型 | 页数 | 字节 | 占在用空间 | 页内未用 |
|---|---:|---:|---:|---:|
| `leaf`（表/索引叶子） | 60,337 | 247,140,352 | **63.75%** | 45,230,153 |
| **`overflow`（大值溢出链）** | **33,894** | **138,829,824** | **35.80%** | 876,680 |
| `internal`（B 树内部节点） | 447 | 1,830,912 | 0.47% | 550,770 |

`conversation_parts` 单表（231,604,224 B）：

| 页类型 | 页数 | 字节 | 占该表 | payload | 页内未用 |
|---|---:|---:|---:|---:|---:|
| `leaf` | 39,096 | 160,137,216 | 69.1% | 129,832,358 | **28,831,837** |
| **`overflow`** | **17,339** | **71,020,544** | **30.7%** | 70,365,098 | 586,090 |
| `internal` | 109 | 446,464 | 0.2% | 0 | 93,343 |

（与 res-sqlite 独立复测逐字一致，含 `unused` 三个子项。）

**三个重要推论：**

1. **全库 138.8 MB 在溢出链里**——这些是超过约 1/4 页（≈980 B）的正文大值被外置存放形成的页链。这部分**正是压缩能直接消灭的**：值一旦压到 980 B 以内就落回 leaf 页，溢出链整条消失。
   → 与 A.5 交叉验证：`parts.content` 里 >1 KB 的行正好占 81.55% 的字节，两者指向同一批数据。
   ⚠️ **但 138.8 MB 只是压缩收益的下界，不是全部。** SQLite 对溢出值仍把 maxLocal（≈1 KB）留在 leaf 页，所以 `conversation_parts` 的 **leaf 页还托着 129.8 MB payload**（= content 本地前缀 + `turn_id` 13.2 MB + `attrs_json` 9.8 MB + `id_key` 等），overflow 只有 70.4 MB。**真正的压缩靶子是「leaf payload 129.8 MB + overflow 70.4 MB」两块；只盯 overflow 会低估 1.8 倍。**（leaf/overflow payload 相加 = 200,197,456 = 该表 payload 总和，闭合。）
2. **溢出页几乎不浪费（页内未用仅 0.88 MB）**，真正浪费的是 leaf 页（全库 45.2 MB 页内空闲，其中 `conversation_parts` 28.1 MB）。所以**优化顺序是：先消灭溢出链（靠压缩），再靠 VACUUM 收 leaf 碎片**，不是反过来。
3. `internal` 只有 447 页 / 1.83 MB —— **B 树层级开销可以忽略**。任何"调 `page_size` 来减少树层数"的方案，天花板是 1.8 MB，不值得做。

> 与 res-sqlite 的分工：他们指出"`parts.content` 的溢出页是 220 MiB 的主因"，实测更精确的说法是 **30.7%（71.0 MB）来自溢出页，69.1%（160.1 MB）仍在 leaf 页**。所以结构性瘦身有两条腿——**压缩（打溢出链）+ 列宽（`turn_id` 等 TEXT UUID）**，缺一不可。

**5,213 个 `.idx` 文件**——正常合并后的索引应该是个位数 segment。

### B.2 有效 vs 废弃（这是核心发现）

| 代数 | 字节 | segment 数 | 状态 |
|---|---:|---:|---|
| `d86f8bf5/generation-47f251c3…` | 0.989 GiB | 72 | 孤儿实例（`conversation_search_index_state` 无对应行） |
| `bca14ae6/generation-3af6321a…` | 0.364 GiB | 92 | 上一代，已被超越 |
| `d86f8bf5/generation-98929d2c…` | 0.343 GiB | 53 | 孤儿实例，opstamp=91,615（远落后） |
| **`bca14ae6/generation-8e175746…`** | **0.318 GiB** | **93** | **← 当前 ACTIVE** |
| 合计有效 | 2.013 GiB | 310 | |
| **81 个 `generation-*.tmp` 目录** | **22.677 GiB** | — | **全部 meta.json 为 `opstamp=0, segments=0`** |

`conversation_search_index_state` 的真实记录：

```
health = ready
document_count = 25,022
size_bytes = 301,611,440        (287.6 MiB — 应用自认为的索引体积)
active_generation = generation-8e175746…
```

**应用认为索引是 287 MiB，磁盘上是 24.69 GiB，相差 85 倍。**

关键在于：`size_bytes` **只累加 `active_generation` 那一代的文件**，`generation-*.tmp` 和旧代数完全不计入。所以**这个问题在任何健康检查、体积监控、UI 显示里都是完全不可见的**——应用会一直报告"索引 288 MB，健康"，而磁盘每天多几个 GB。这就是它长到 24.69 GiB 都没被发现的原因。

那 81 个 `.tmp` 目录的 `meta.json` 全部写着 `opstamp=0, segments=0`，但目录里躺着几百 MB 已写出的 segment 文件——这是典型的 **Tantivy `IndexWriter` 在 commit 前被杀死/超时中断**：segment 文件已落盘，却从未写进 `meta.json`，于是永不可达、永不回收。每次失败的重建都会新开一个 `generation-*.tmp`，于是 81 次失败 = 22.68 GiB 垃圾。单个最大的垃圾代 2.09 GiB / 5,944 文件。

### B.3 活跃代内部构成（回答"主要占用来自哪些 segment 文件"）

| 文件类型 | 体积 | 占比 |
|---|---:|---:|
| `.term` | 151.6 MiB | **46.6%** |
| `.pos` | 91.7 MiB | 28.2% |
| `.idx` | 78.5 MiB | 24.1% |
| `.store` | 2.8 MiB | 0.8% |
| `.fieldnorm` | 0.7 MiB | 0.2% |

**关键：`.store` 只有 2.8 MiB。正文根本没有进索引**，索引体积 98% 花在倒排词典 + 位置表 + posting 上。

25,022 文档撑起 325 MiB 索引 = **13.3 KB/文档**。这个比值极不正常（正常英文全文索引约 1~3 KB/文档），说明 term 已经爆炸——最可能的原因是中文按字/ngram 切词，或者 `position` 对超长正文（p99 = 12 KB、max = 218 KB）逐 token 记录偏移。

### B.4 是否存在大量未合并 segment

**是。活跃代 93 个 segment / 25,022 文档 = 258 文档/segment。**

- Tantivy 默认的 `LogMergePolicy` 会持续把 segment 合并到个位数；93 个说明**合并线程从未有机会跑完**（与 `.tmp` 泄漏同源：进程活不到 merge 那一步）。
- 后果直接体现在 `.term` 占 46.6%：93 个 segment 各自持有一份高度重叠的词典，`FST` 无法跨 segment 共享。
- 保守估计：**把 93 个 segment 合并成 1~4 个，`.term` 至少能砍 30~50%**，即活跃索引从 325 MiB 降到 200 MiB 左右。此项未经实际 merge 验证，标注为推断。

### B.5 索引的账

- 磁盘实占：**24.69 GiB**
- 应有体积：**0.32 GiB**（当前 active 代）或 0.99 GiB（含另一实例的最新代）
- **可立即回收：22.68 GiB，回收率 91.8%，零代码、零风险（`.tmp` 目录在 Tantivy 语义上就是不可达垃圾）**

### C.5.1 块级模型的写放大约束（已与代码侧核对，结论：可行）

我原先只写"单行原地 UPDATE 会放大成整块重写，需 slack 或 CoW"，属**过度保守**。路径侧核过写入路径后，实际情况是**主流写入是整包替换，块级天然友好**：

| 写入路径 | 语义 | 对块级的影响 |
|---|---|---|
| **`snapshot.rs:431-470`（唯一写入口）** | `DELETE FROM parts WHERE turn_id IN (…session_id=?)` → `DELETE FROM turns` → 逐条 `INSERT`，**整个会话全删全插，无 UPDATE** | ✅ **完全友好**：块可按会话边界整体重算，不需要 slack、不需要 CoW |
| 调用它的 6 处（`import.rs:142`、`import_single.rs:57`、`web_record_repo/import.rs:68`、`reproject.rs:297+366`、`subagent_fold.rs:319+328`） | 同一语义（含子代理折算、重解析，都是重算整会话再整包替换） | ✅ 友好 |

**但有 5 处原地 UPDATE 会打破这个友好性**（按影响排序列出）：

| 位置 | 改哪列 | 频率 | 影响 |
|---|---|---|---|
| `conversation_repo/projection.rs:12-24` | `parts.translated_text` | 每次翻译一条 | 中 |
| `web_record_repo/list.rs:389-405` | `web_record_parts.translated_text` | 同上 | 中 |
| **`conversation_repo/triad_update.rs:74`** | `turns.process = ?1`（**整段 JSON 覆写**） | 翻译回填 | **重：`process` 列 33.4 MB，整段重写** |
| `store/database.rs:257-264` | `parts.attrs_json = json_remove(...)` | 一次性自愈（checksum 匹配才跑） | 中，低频 |
| **`store/path_convergence.rs:107-142,150-167`** | 启动期 `UPDATE process/attrs_json`（全表 GLOB 扫描） | **每次启动** | **重：冷路径但触发大量块重写** |

**折中方案（推荐）：只对 `content` / `process` / `attrs_json` 走块级；`translated_text` 保持逐行或明文。**

这条折中在本机数据上**几乎零成本**——实测 `translated_text` 基本是空的：

| 列 | 非空行数 | 字节 |
|---|---:|---:|
| `conversation_parts.translated_text` | **3** | 6,812 |
| `web_record_parts.translated_text` | **1** | 219 |
| 合计 | 4 | **7,031 B（6.9 KiB）** |

→ 把 7 KB 的列留在逐行模型，等于不付代价地消除了 2 处高频原地 UPDATE。
剩余痛点是 `triad_update.rs:74`（`process` 整段覆写）和 `path_convergence.rs`（启动期全表扫）。后者可用"收敛过一次就置位"消除；前者可在翻译回填时按"整会话重算 + 整包替换"复用 snapshot 路径来规避。

**结论：块级的写放大问题是可解的，不是硬阻断。** 只有在"既不接受状态位优化、又要求高频随机单行更新"的前提下，才需要退回逐行模型（损失 49 MiB）。


### C.6 决定压缩比的是「块大小」，不是「分组方式」（实测排除）

直觉上"把同一轮对话的 prompt/process/response 打包在一起"应该比"按列分开压"更好（时间局部性）。**实测相反。**

`conversation_turns` 三列合计 64,334,861 B，四种打包方式全量实测：

| 打包方式 | 平均块大小 | 压缩比 | 节省 |
|---|---:|---:|---:|
| 逐轮打包（一轮 = prompt+process+response 拼一条） | 8.8 KB | **2.826** | 64.62% |
| **逐轮打包 + 4 MB 分块拼接** | 4 MB | **4.929** | 79.71% |
| 按列分开 + 4 MB 分块（`prompt`） | 4 MB | **8.091** | 87.64% |
| 按列分开 + 4 MB 分块（`process`） | 4 MB | **6.642** | 84.94% |
| 按列分开 + 4 MB 分块（`response`） | 4 MB | **2.988** | 66.53% |
| 三列分别 4 MB 分块的加权合计 | 4 MB | 5.031 | 80.13% |

**结论：**
1. **2.826 → 4.929 的跃升全部来自块大小（8.8 KB → 4 MB）**，与"是否按轮聚簇"无关。
2. 轮级打包（4.929）vs 列式分离（5.031）**只差 2%**——聚簇方式几乎无关紧要。
3. 所以路径侧"压缩单位应取会话级/轮次级而非行级"的方向对，**但规格不够**：轮级只有 2.83x，必须到 **MB 级块**才有 4.9~5.4x。建议把结论改写成「**压缩单位必须是 MB 级块**」，而不是「轮次级」。
4. 副产品：`prompt` 单列 4 MB 分块能到 **8.09x**，是全部列里最高的——再次印证它的重复性（D.2 去重率 36.7%）。**内容相似性 > 时间局部性。**

### C.7 「阈值分流」只在逐行模型下成立（一处重要的口径澄清）

**本节回答一个容易误用的地方。** 我此前在多处写"`parts.content` 必须按阈值分流"，这个结论**只在逐行压缩模型下成立**，不能套到块级模型上：

| 设计 | 是否需要阈值分流 | 原因 |
|---|---|---|
| **逐行压缩**（每行一个独立 zstd frame） | **必须** | 275 B 的行压完 252 B，还要挂 frame 头（magic 4 B + frame_header 2~6 B + content_checksum 0/4 B）。用 `ZSTD_c_contentSizeFlag=0` + 关闭 checksum 可压到约 10 B 头，但 <256 B 桶的实测比只有 **1.092**，即**净收益 ≈ 0，甚至为负**。 |
| **块级模型**（多行拼进 4 MB block） | **完全不需要** | 小行不单独成 frame、不单独付头开销，只是 block 里的若干字节。多进来的 74,943 行小文本合计仅 9.18 MB，它们混在 4 MB 块里对压缩比**没有负面影响**，反而因为"上下文更多"略微提升比值。 |

**验证**：块级模型下若强行剔除 <256 B 的行，`parts.content` 的输入从 169,955,233 B 降到 160,779,674 B，但压缩产物从 31,576,779 B 只降到 30,023,000 左右（同比例）——**剔除去掉的 9.18 MB 里，本来也只对应约 1.5 MB 压缩产物**。为省这 1.5 MB 引入一层分流逻辑（判断、双路径、两套读逻辑），不划算。

> **结论修正（采纳路径侧质疑）**：
> - **逐行模型**：`parts.content` 需要 >1 KB 阈值；`turns.process` 不需要（85.1% 字节在 >4 KB 行里）。两列策略不同。
> - **块级模型**：**所有列同一策略——直接整列拼块压缩，不需要任何阈值判断**。列的差异只体现在压缩比（`attrs_json` 18.2x … `turns.response` 2.99x），不体现在处理方式上。
> - 因此"两列形状相反"这个观察**只在逐行模型下有意义**；块级模型下它是纯观测事实，不产生任何实现分支。

## D. 去重率实证

> 方法说明：按 **4 KB 分块**（近似 BLAKE3 的块语义），**用 `sha256` 代替 BLAKE3** 计算块哈希。

| 占该列正文比例 | **11.84%** |

对比 D.2 里同列的 4 KB 分块去重率 **12.20%**——两者几乎相等。
**说明去重收益几乎全部来自"整行逐字节相同"，而不是"行内/行间的部分重叠"。**

**决策含义**：如果目标只是这 11%，**用整行内容哈希做主键（content-addressed）就够了，不需要 BLAKE3 大块 CDC 分块**。4 KB 分块换来的额外收益 < 0.4 个百分点，却要引入分块表、块引用计数、GC 等一整套复杂度。**"大块去重"在这个数据集上属于过度设计。**

### D.4 重复块的典型来源

按 `kind` 字段统计重复正文的出现次数（Top）：

| kind | 重复组数 |
|---|---:|
| `antigravity.file-change` | 2,847 |
| `antigravity.tool` | 1,696 |
| `antigravity.reasoning` | 1,529 |
| `codebuddy.reasoning` | 1,505 |
| `codebuddy.tool` | 1,315 |
| `antigravity.result` | 1,042 |
| `antigravity.ambient` | 809 |
| `codex.reasoning` | 243 |
| `codex.result` | 182 |
| `codebuddy.result` | 144 |
| `codex.ambient` | 133 |
| `opencode.result` | 115 |

分布高度集中在 **tool 调用 / reasoning / file-change / ambient** 这四类结构化小部件上，而不是人类自然语言。

**跨会话 vs 同会话**（11,883 个重复正文值）：

| 范围 | 组数 | 占比 |
|---|---:|---:|
| 跨会话重复 | 9,247 | **77.8%** |
| 同会话重复 | 2,636 | 22.2% |

**结论：去重作用域必须是全局的，不能按会话。** 如果只在单个会话内去重，只能拿到 22% 的收益。

**交叉验证**：`conversation_sessions` 2,109 条中，`user_visible=0` 且 `execution_origin='subagent'` 的有 **903 条（42.8%）**。子代理会话占了近一半——这与"跨会话重复占 78%"高度吻合：父会话与子代理各记一份同样的工具调用与推理过程，就是重复的主要机制。

### D.5 关键反直觉发现：去重与块压缩高度重叠

在同一份 200 行抽样上做三组对比：

| 处理 | 字节 |
|---|---:|
| 原始 | 1,626,509 |
| 只做 Zstd-3（拼块） | 250,597 |
| 先去重（4 KB）再 Zstd-3（拼块） | 250,552 |
| 差额 | **45 B（0.02%）** |

**先去重再压缩，几乎一字节都没多省。** 原因很直接：Zstd 的 4 MB 窗口本身就在做"重复匹配"，块编码器已经把重复块替换成了 3 字节的 offset/length 引用，比 BLAKE3 的分块表还要省。

**所以：**
- 如果走**批量/列式压缩**路线 → BLAKE3 去重基本没有增量价值，别做。
- 如果走**逐行压缩**路线 → 去重才有意义（每行独立压缩，窗口太小，只有几十~几千字节，zstd 找不到跨行的重复），此时 11.33% 去重 + 逐行 Zstd 是叠加的。
- 如果只是想在**不压缩**的前提下省空间 → 整行哈希去重，收 11.84%。

## E. 结论与优先级

### E.1 主库最终能压到多少

| 阶段 | 主库大小 | 说明 |
|---|---:|---|
| 现状 | **1.72 GB**（+35 MB WAL） | 其中 1.24 GiB 是空闲页 |
| ① `VACUUM` | **≈388 MB**（370 MiB） | 回收 1.24 GiB，纯 SQLite，无代码 |
| ②A + **块级压缩**（4 MB 打包，全量实测 5.241x） | **≈186 MB**（177 MiB） | 正文 265.6 MB → 48.3 MiB，回收 **205.0 MiB**；含块索引开销 ~3 MB |
| ②B + 逐行 Zstd(>1 KB 阈值)（保守方案） | ≈225 MB（215 MiB） | 正文 → 98 MB，回收 163.6 MB；无写放大 |
| ③ 逐行方案再叠整行哈希去重(11.33%) | ≈209 MB（200 MiB） | 仅在逐行模型下有意义；块级模型下去重无增量（D.5） |

**两条终点，按写放大约束二选一：**
- **块级模型（推荐）：1.72 GB → 186 MB（-89.2%，9.2 倍）**，正文压缩 **205.0 MiB**，代码更简单（无阈值、无 frame 头）。
- **逐行模型（保守）：1.72 GB → 209 MB（-87.8%，8.2 倍）**，无写放大，但每行要挂 frame 头，且需阈值分流。
- 两者相比，块级多省 23 MB。**写放大不是硬阻断**（见 C.5.1）：主流写入是整会话 DELETE + INSERT，块可按会话边界整体重算；只要把 `translated_text`（实测全库仅 **6.9 KiB**/4 行）留在逐行模型，块级的不良 UPDATE 面就只剩 `triad_update.rs:74` 与 `path_convergence.rs` 两处，且都可用"整会话重算"或"收敛置位"消除。**建议直接上块级。**

但无论哪条，**1.24 GiB（占总收益的 74%）都来自 `VACUUM` 一行命令**；整个"压缩 + 去重"工程只贡献 163~205 MiB。

**分期切分点（若 P2 要分多期上线）**——块级模型下各列收益极不均匀：

| 列 | 块级比 | 省下字节 | 占总收益 |
|---|---:|---:|---:|
| **`parts.content`** | 5.382 | **138,378,454** | **64.4%** |
| `turns.process` | 6.642 | 28,407,659 | 13.2% |
| `turns.response` | 2.988 | 12,395,856 | 5.8% |
| `turns.prompt` | 8.091 | 10,744,612 | 5.0% |
| `parts.attrs_json` | 18.221 | 9,298,900 | 4.3% |
| `wr_parts.content` | 7.123 | 8,453,009 | 3.9% |
| `wr_turns.response` | 2.625 | 6,593,248 | 3.1% |
| `wr_turns.prompt` + `wr_turns.process` | 2.855 / 87.3 | 687,747 | 0.3% |
| **合计** | **5.241** | **214,959,485（205.0 MiB）** | 100% |

**第一期只做 `parts.content` 就能拿到 64.4% 的收益，且完全不触碰 `turns.process` 的整段覆写风险**（`triad_update.rs:74`）。这是风险最低的切分点，建议作为 P2 的默认分期方式。

**三期切分（收益与风险对齐）**

| 期 | 范围 | 收益 | 累计 | 主要风险 |
|---|---|---:|---:|---|

| 三期 | 其余 4 列（`prompt`/`response`/`wr_*`） | 38,874,472（18.1%） | 100% | 无 |

### E.2 25 GB 索引是否才是第一优化目标

**是，而且不是"优化"级别，是"止血"级别。**

- 索引目录 24.69 GiB = 整个 `~/.assetiweave`（48.3 GiB）的 **51%**
- 其中 **22.68 GiB（91.8%）是 81 个 `.tmp` 废弃代数——纯垃圾，可直接 `rm -rf`**
- 有效索引只有 **0.32 GiB**
- 索引 : 主库 体积比 = **15.4 : 1**，而索引只含 25,022 个文档、连正文都不存（`.store` 仅 2.8 MiB）

**索引不是"太大"，是"漏了"。** 一个 25,022 文档的元数据索引占了 24.69 GiB，这件事本身说明构建流程有缺陷（writer 被杀 → 每次重试留下一个 200 MB~2 GB 的 `.tmp`）。

### E.3 优先级建议

| 优先级 | 动作 | 收益 | 工作量 | 风险 |
|---|---|---:|---|---|
| **P0** | 清理 81 个 `generation-*.tmp` 废弃目录 | **22.68 GiB** | 极低（一个 find/rm） | 极低（Tantivy 语义上不可达） |
| **P0** | `VACUUM` 主库 | **1.24 GiB** | 极低 | 低（需 2×磁盘瞬时余量；当前 586 GiB 可用，充足） |
| **P0** | 修 `.tmp` 泄漏根因（writer 中断/超时 → 清理逻辑） | 防止每天再涨 GB 级 | 中 | — |
| **P1** | 确认后清理 7 个 `app.db.bak_*` | **11.21 GiB** | 极低 | 中（需确认无回滚需求） |
| **P1** | 建孤儿副本清理策略（白名单命名 + 尺寸等于某代主库 → 判为孤儿）；`auto_vacuum=INCREMENTAL` 防碎片复发 | 防止 1.24 GiB 复发 + 防止再攒 11 GiB 裸副本 | 低 | — |
| **P2（附带）** | 补备份降级可观测性：`or_else` 打 `warn!` 并回填降级标记；产物断言 `freelist_count≈0`；`quick_check` 升级为尺寸+freelist 双校验（**无需改 `busy_timeout`，默认 5000 ms 已够**） | 让"压缩效果"可被自证；无可回收字节，纯可观测性 | 低 | — |
| **P1** | 修 Tantivy merge 饥饿（93 segment → 1~4） | 索引 ~-35%（~110 MiB） | 中 | 中 |

> **给拍板的口径约束（务必写进对外表述）**
>
> **不要承诺「上了压缩，磁盘立刻下降」。** 压缩只作用于主库那 1.60 GiB 一档；即使压到 209 MB，机器上 `~/.assetiweave` 的占用仍然从 **~37.1 GiB（= 48.3 − 11.2 备份）起步**，因为 22.68 GiB 的索引垃圾和 11.21 GiB 的裸副本与压缩完全无关。
> 顺序反了的话，用户会看到「做了压缩方案、磁盘几乎没变」的负面对比。**先清理、后压缩，叙事才不会翻车。**
>
> 三笔账要分开报，不能加总成一个数：
> - **索引泄漏 22.68 GiB**（可立即回收，无需任何功能开发）
> - **裸副本 11.21 GiB**（可立即回收，需确认无回滚需求）
> - **主库碎片+正文 1.60 GiB → 208 MiB**（VACUUM 是免费的，压缩去重要做工程）

### E.4 面向"日均 3 亿 Token"的容量推算

现有全库正文 253.3 MiB，约 2.45 亿字符；按混合中英 ~3 字符/token 估算 ≈ **8,200 万 token**。

- 3 亿 token/天 ≈ **每天把现有全库写 3.7 遍**
- 原始正文增长 ≈ **0.96 GB/天 ≈ 350 GB/年**
- 逐行 Zstd（2.6x）→ **0.37 GB/天 ≈ 135 GB/年**
- 列式/分块 Zstd（5.38x）→ **0.18 GB/天 ≈ 65 GB/年**

（token→字节 换算是粗估，假设已在正文中说明；结论对 ±30% 的偏差不敏感。）

**但索引更危险**：按当前 13.3 KB/文档 的比例，正文每涨 1 GB 会带来数 GB 的倒排。**如果 `.tmp` 泄漏和 merge 饥饿不修，索引会以每天 GB 级的速度失控增长，"压缩正文"完全追不上。** 这就是为什么顺序必须是「先治索引、再压正文」。

## 附录 B：实验脚本

完整脚本见 `/tmp/wayfinder-209/_probe_cd.py`，原始输出见 `/tmp/wayfinder-209/_probe_out.json`。
核心做法：

1. **Zstd 绑定**：`ctypes.CDLL("/opt/homebrew/lib/libzstd.dylib")`，复用单个 `CCtx` / `DCtx` 避免每次分配（否则延迟测量会被分配器噪声淹没）。
2. **分层抽样**：对 5 个长度桶各 `ORDER BY rowid LIMIT 40`，总样本上限 50 MB。
3. **比例抽样/全量**：`ORDER BY rowid` 顺序读，按 4 MB 缓冲拼块后一次压缩。
4. **去重**：流式 `fetchmany(2000)`，对每行按 4,096 B 切片，`sha256` 摘要入 `set`；只保留 32 B 摘要，不保留正文。峰值内存 ≈ 摘要表（约 5.6 MB）+ 当前批。
5. **隐私**：脚本只输出长度、计数、哈希；正文变量出作用域即释放，全程 `text_factory = bytes`，无任何写盘。

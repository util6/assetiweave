# SPEC：ACP Agent 生命周期去僵尸化与目录真相源对齐

## Problem Statement

用户在 Agent 市场里升级 AntiGravity 时，看到 5 条一模一样的 `binary v1.4.1` 候选，只有第一条可选，其余四条标着「不可用」却不给原因；底部还有一条裸露的 `experimental_verification` 英文字符串，看起来像报错。下载体积显示 301.4 MiB，但实际下的是另一个版本的包。

继续排查后发现这些表象背后是同一类问题：Agent 生命周期这条链路上，业务早就切换到 ACP-only + 应用级安装表，但**旧的表、旧的分发类型、旧的协议后端、旧的迁移逻辑都还留在产品和代码里，既没有被删除，也没有被标记为废弃**。

用户（产品视角）实际承受的后果：

1. **无法判断该选哪一个**。候选列表把 5 个平台的二进制包平铺出来，全部叫 `binary`，没有操作系统、架构、安装位置任何区分信息，不可用的四条也不说明为什么不可用。
2. **看到自己看不懂的东西**。`experimental_verification` 这种后端错误码直接渲染成界面文字，用户不知道这是警告、是报错，还是需要处理。
3. **看到不真实的数字**。预览显示的下载体积和实际下载的包不是同一个版本。
4. **整机不可用而没有任何解释**。Intel Mac 用户在目录里根本没有对应分发，连预览对话框都进不去，只得到一个 `distribution_unsupported`。
5. **维护者无法信任目录与证据**。内置目录把 AntiGravity 钉在 1.1.1，上游已经 1.4.1；发布证据里记录的目录哈希与当前目录文件对不上；远端目录缓存停留在两个月前。
6. **清理工作缺乏准绳**。仓库里有一批没有任何代码引用、但仍留在生产数据库中的表；更糟的是"零僵尸表核验"测试把这些废弃表写进了"必须存在"清单，等于把僵尸固化成规范。

## Solution

把 Agent 市场这条链路收敛到**一个真相源、一条协议、一套分发类型**，并把所有已经不在业务里的东西真正删除，而不是继续留在库里和代码里。

1. **清退三张已被取代的安装/适配器包表**，并修正"零僵尸表核验"测试，使其校验"废弃表必须不存在"而不是把它们写进期望清单。
2. **移除 Native 协议后端整条执行路径**，Agent 执行只剩 ACP 一条路；历史遗留的 native 定义在读取时降级为「不兼容」，不再尝试执行。
3. **分发类型收敛为 binary / npx 两种**，删除 system 与 uvx 两条选择分支，以及每次预览都要探测 `uv` 的多余宿主探测。
4. **删除永远不可能成功的遗留能力分配迁移**，其兼容职责下沉到设置 schema 版本迁移，一次性完成。
5. **目录不再说谎**：bundled 目录由上游快照生成，体积与校验和缺失时显示「未知」而不是沿用旧值；不可校验的下载在预览里明确标注「未校验」；发布证据与目录内容哈希由 CI 强制对齐。
6. **分发候选的输出契约带上平台事实与不可用原因**，前端据此只展示本平台候选、跨平台收进折叠区，并把不可用原因写成用户能读懂的一句话。
7. **后端警告改为结构化 code**，前端维护 code → 文案映射，杜绝 snake_case 直接漏到界面。

## User Stories

### 分发候选与平台事实

1. 作为使用 Apple Silicon Mac 的用户，我希望能直接看到"macOS · Apple Silicon"这样的分发名称，而不是五条都叫 binary，这样我能一眼确认系统选的是我本机的包。
2. 作为使用 Windows 的用户，我希望市场里只列出 Windows 可用的分发，这样我不会误以为自己在下载 mac 版。
3. 作为高级用户，我希望跨平台的其他分发被收进一个折叠区（例如「其他平台 (4)」），这样我既不会被噪音干扰，又能确认这个 Agent 支持哪些平台。
4. 作为用户，我希望不可用的分发明确写出原因（例如「仅适用于 Linux x86_64」），而不是只显示一个「不可用」。
5. 作为 Intel Mac 用户，我希望要么能看到可安装的 x86_64 分发，要么在市场上明确告知该 Agent 暂不支持我的机型，而不是在点击后收到一个错误码。
6. 作为用户，我希望当前选中的分发在视觉上是"选中"而不是"禁用"，这样我不会误以为它点了没反应。
7. 作为用户，当只剩一个可用分发时，我希望界面不要再用「分发方式」这种分组标题加一个「已选择」徽章来占位，而是直接把平台与体积并进头部摘要。
8. 作为用户，我希望分发排序优先把本平台可选的分发放在最前，而不是依赖分发 ID 的字典序巧合。

### 版本与体积的真实性

9. 作为用户，我希望预览里的下载体积对应我真正要下载的那个版本，这样我能判断流量成本。
10. 作为用户，当上游没有提供体积信息时，我希望显示「未知」而不是显示一个过期版本的数字。
11. 作为用户，当上游没有提供校验和时，我希望预览明确提示「本次下载不做完整性校验」，这样我能自己决定是否继续。
12. 作为用户，我希望升级目标版本号来自上游真实发布，而不是来自一个已经过期两个月的本地目录。
13. 作为用户，我希望目录刷新后能看到"目录数据生成于何时"，这样我知道自己看到的信息有多新。

### 警告与错误表达

14. 作为用户，我不希望在界面上看到 `experimental_verification` 这类后端标识符，我希望看到一句人话，例如「该 Agent 尚未完成完整验证，升级后可能出现协议兼容问题」。
15. 作为用户，我希望警告有标题和图标，与错误区分开，这样我能判断它是否阻塞操作。
16. 作为用户，我希望警告不阻止我继续操作（当前确实不阻止），并且界面上能看出这一点。
17. 作为 CLI 用户，我希望 `aiwc` 输出的警告是稳定的枚举 code，这样我的脚本可以按键判断，而不必匹配中文文案。
18. 作为前端开发者，我希望后端只下发 code、前端独占文案映射，这样新增警告时不需要改后端。

### 数据与代码清理

19. 作为维护者，我希望生产数据库里不再存在任何"没有任何代码引用"的表，这样我排查问题时不需要先猜哪张表是真的。
20. 作为维护者，我希望"零僵尸表核验"测试校验的是"废弃表必须已被删除"，而不是把废弃表写进必须存在的清单。
21. 作为维护者，我希望 Agent 执行只有 ACP 一条实现路径，这样我阅读执行链路时不需要同时维护两套心智模型。
22. 作为维护者，我希望早年被标为 Native 的历史安装记录在读取时被判为「不兼容」并提示重装，而不是尝试加载一个已删除的后端。
23. 作为维护者，我希望分发类型只有 binary 与 npx 两种，这样目录契约、选择器、安装器、前端渲染的分支数是可控的。
24. 作为维护者，我希望启动阶段不再执行一个永远走不到安装分支的遗留迁移，这样启动日志里不会出现无意义的能力分配提示。
25. 作为维护者，我希望前端不再维护一份包含"目录里不存在"的 Agent 的静态展示列表，这样能力分配下拉里不会出现装不了的条目。
26. 作为维护者，我希望迁移文件的版本号位数统一，这样我按文件名排序就能推断真实执行顺序。

### 发布与证据

27. 作为发布者，我希望发布证据里记录的目录内容哈希与随包发布的目录文件一致，这样证据是可验证的。
28. 作为发布者，我希望目录版本滞后于上游超过阈值时，发布流程直接失败，而不是靠安装时重写下载地址来兜底。
29. 作为用户，我希望升级完成后看到的版本号，与我在预览里确认的版本号一致。

## Implementation Decisions

### 模块范围

- **Agent 市场领域层**：分发选择器、分发候选契约、分发类型枚举。
- **ACP 引擎中台 (`backend/agent_engine`)**：承接从 `asset_core` 下沉的 ACP 握手探活（`probes_acp` / `probes_acp_health`）、运行时定义与模型缓存（`definition` / `model_cache`）及 ACP 运行时物化（`materialize`），保持零数据库依赖；彻底移除 `asset_core` 对 `agent-client-protocol` 的直接依赖。
- **扩展内核 (`backend/asset_core/src/infrastructure/extensions/`)**：承接从 `infrastructure/agent_market/` 迁入的通用包下载与归档解压（`binary` / `npx`）、版本目录布局（`layout` 含 `cleanup_runtime_directories`）、包清单校验（`manifest`）与上游版本探测（`upstream_probe`）；彻底删除 `backend/asset_core/src/infrastructure/agent_market/` 目录。
- **统一插件存储层**：以统一的 `app_extensions`、`app_extension_versions`、`app_extension_catalog_releases` 三表模型承载外部桥梁插件（`agent.acp` 与 `conversation.adapter`）的安装、多版本留存与市场目录缓存（详见 [ADR-0019](../../adr/0019-unified-extension-market-and-capability-seams.md)）。
- **应用门面 (`AppService`)**：保持现有 Agent 市场与对话适配器 Tauri / CLI 对外命令签名兼容，内部统一读写 `app_extensions` 三表与 `extensions` 内核。
- **前端 Agent 设置面板**：市场列表、安装预览对话框、能力分配下拉。
- **数据库迁移与收敛测试**。

### 决策 1：一步到位收敛为统一插件市场三表模型，清退全部 8 张新旧分裂表

- 遵循 [ADR-0019](../../adr/0019-unified-extension-market-and-capability-seams.md)，新建统一的插件市场三表：
  1. `app_extensions`（已安装插件主表：公共生命周期列 + 不设死板二选一 `CHECK` 的 `capability_kind` + `target_id` 唯一索引 + 类型化 `capability_meta_json`）。
  2. `app_extension_versions`（插件已安装多版本留存表：`(extension_id, version)` 主键，外键级联 `app_extensions`）。
  3. `app_extension_catalog_releases`（统一插件市场目录与版本缓存表：`(catalog_source, extension_id, version)` 主键，取代散落在 `~/.assetiweave/cache/agent-market/*.json` 的本地缓存文件）。
- 在同一条 14 位 SQLx 迁移中：
  - 将现有 `app_agent_installations`、`app_conversation_adapter_packages`、`app_conversation_adapter_package_versions`、`app_conversation_adapter_catalog_releases` 中的有效数据无损迁入上述 3 张新表；
  - 迁入时遇到历史 `protocol = 'native'` 或 `distribution_type IN ('system', 'uvx')` 的记录，自动降级标记为 `installation_status = 'incompatible'`、`runtime_status = 'failed'`、`error_code = 'agent_reinstall_required'`；
  - 迁移完成后，按先子表后主表顺序一次性 `DROP TABLE IF EXISTS` 全部 **8 张旧表**（4 张无前缀历史僵尸表 `agent_installations`、`conversation_adapter_packages`、`conversation_adapter_package_versions`、`conversation_adapter_catalog_releases` + 4 张原分裂 `app_*` 表），免除冗余的外部文件转储，并移除 `database.rs` 中针对旧表的 `repair_known_modified_catalog_release_migration` 修复钩子。
- 修正现有"零僵尸表核验"（`database_tests.rs`）：将 SQL 查询过滤条件扩展为覆盖 `agent_%` 与 `app_%`，断言上述 8 张旧表全部不存在，且 `app_extensions`、`app_extension_versions`、`app_extension_catalog_releases`（及 `app_shortcut_items`）精确匹配期望白名单。

### 决策 2：Native 协议后端分两步退场

- **第一步（本次）**：删除 native 执行后端与其执行分支，执行器只保留 ACP。协议枚举保留 `Native` 变体，仅用于反序列化历史 `definition_json`；读取到 native 定义时直接判为「不兼容」并给出「请重新安装」结论，不再尝试启动进程。
- **第二步（后续）**：待确认生产环境不再存在 native 定义后，删除枚举变体与所有 `matches!` 分支。
- 依据：当前目录八个条目全部为 ACP，应用级安装表内无 native 记录；分两步是为了让历史数据有明确的降级出口，而不是直接报错。
- 受影响字段：`resume_args` 仅对 native 生效，随第一步一并移出能力模型。

### 决策 3：分发类型收敛为 binary / npx

- 目录契约只保留 `binary` 与 `npx` 两种分发；`system` 与 `uvx` 从契约、选择器、排序权重、候选构造中移除。
- 删除宿主探测中的 `uv` 探测；保留 `node` / `npm` 探测（npx 分发的前置条件）。
- 删除"探测本机 system 分发"的预览前置动作。
- 目录 schema 变更需在目录校验中显式拒绝 `system` / `uvx`，防止旧目录被加载后行为分叉。

### 决策 4：删除遗留能力分配迁移

- 移除启动阶段执行的遗留能力分配迁移。该迁移只在条目存在 system 分发时才执行安装，当前目录无 system 分发，因此永远只会产出"需要确认"的提示噪音。
- 兼容职责下沉：能力分配引用的合法性由设置 schema 版本迁移一次性校验，非法引用在迁移时清除并写入一次性公告，而不是每次启动重试。
- 设置中遗留的迁移标记字段在迁移完成后清理。

### 决策 5：目录不再说谎

- **bundled 目录生成**：由上游快照生成，只写入上游真实提供的 `size` 与 `sha256`；缺失即为 `null`，禁止沿用旧值或从旧 URL 推断。
- **预览展示**：体积为 `null` 时显示「未知」；校验和为 `null` 时在预览中显式标注「本次下载不做完整性校验」，该项属于确认前必须可见的信息。
- **版本一致性**：升级目标版本只能来自上游探测结果；预览展示的目标版本、实际下载的版本、写入安装记录的版本必须是同一个值，三者由同一处解析产生。
- **过期兜底移除**：删除"安装时按版本号字符串替换下载 URL"的兜底改写逻辑；若上游未提供对应平台的目标，直接判定该分发不可用并给出原因。
- **发布证据**：发布证据中的目录内容哈希必须等于随包目录文件的实际哈希；CI 增加校验（复用现有的目录发布检查脚本入口）。
- **目录新鲜度**：市场列表需暴露目录数据的生成时间与来源（bundled / 远端缓存）；远端缓存超过阈值时在界面上提示"目录数据已过期"，不引入后台自动轮询（属 #91 边界之外）。

### 决策 6：分发候选契约扩展

- 候选新增：目标操作系统、目标架构、是否为当前平台、是否为当前平台首选。
- `reasonCode` 改为**不可用时的必填项**，并在渲染优先级上高于版本号展示；不可用原因不得被"有版本号"掩盖。
- 候选排序：本平台可选 → 本平台指定 → 其他平台；同组内按分发类型再按标识稳定排序。
- 推荐标记只允许落在可选项上。

### 决策 7：后端警告结构化

- 安装预览的 `warnings` 从字符串数组改为结构化条目：稳定 code + 可选参数。
- 前端维护 code → 文案映射，缺映射时兜底为一句通用说明，禁止直接渲染 code。
- 现有 `experimental_verification` 对应文案：「该 Agent 尚未完成完整验证，升级后可能出现协议兼容问题」。同类还需覆盖「Agent 正在执行中」「能力分配未清理」等既有码。

### 决策 8：前端市场与预览

- 市场与预览只渲染本平台候选；跨平台候选收进折叠区并标注数量。
- 分发行标题使用「操作系统 · 架构」，副标题使用分发类型与体积。
- 候选采用单选语义（`aria-checked`），选中项不再使用 disabled 按钮表达。
- 候选仅剩一个时，取消「分发方式」分组标题，平台与体积并入头部摘要区。
- 移除前端静态展示列表中的非目录条目，能力分配下拉只消费市场返回的条目。
- 视觉遵循既有设计系统：候选卡 `rounded-xl`，徽章胶囊，警告框带标题与图标并与冲突框在配色语义上区分。

### 决策 9：迁移版本号全量统一为 14 位与本地账本自愈

- 将 `backend/asset_core/migrations/` 下全部 76 个 12 位历史迁移文件名统一重命名为 14 位（`YYYYMMDDNNNN` $\rightarrow$ `YYYYMMDD00NNNN`），消除按整数排序时的新旧错位。
- 在 `database.rs::open_migrated_pool` 调用 `MIGRATOR.run(&pool)` 之前前置执行 `_sqlx_migrations` 账本自愈 SQL（`UPDATE _sqlx_migrations SET version = (version / 10000) * 1000000 + (version % 10000) WHERE version < 10000000000000`），并同步更新 `database.rs` 与 `database_tests.rs` 中的硬编码历史版本号。
- 增加单测门禁，强制校验 `migrations/` 目录下所有 `.sql` 文件名前缀必须为 14 位数字。
- 本次收敛迁移的 DROP 语句需与既有"废弃表清退"风格一致：先子表后主表，全部使用 `IF EXISTS`。

## Testing Decisions

### 什么算好测试

只断言外部可观察行为，不断言内部实现细节。具体到本次：

- 断言"预览返回了哪些候选、每个候选的可选性与原因"，而不是断言选择器内部的匹配写法。
- 断言"迁移后的表清单里没有废弃表"，而不是断言某条 DROP 语句存在。
- 断言"同样输入下，预览体积与实际下载源一致"，而不是断言 URL 拼接规则。
- 不为了测试而扩大业务 API 可见性；测试文件与业务实现分离，遵循仓库既有的同级 `*_tests.rs` 约定。

### 接缝一（行为，最高点）：Agent 市场应用门面

安装预览、市场列表、安装启动三者是所有消费方（Tauri 命令、CLI、前端）的唯一收口，测试全部打在这一层：

- 平台过滤：模拟不同 `os` / `arch` 上下文，断言候选集合与"是否当前平台"标记。
- 不可用原因：断言不可用候选必带 `reasonCode`，且不会因为存在版本号而被吞掉。
- 版本一致性：断言预览目标版本、下载源版本、安装记录版本三者相等。
- 体积与校验：断言上游缺失体积时为 `null`（前端展示「未知」），缺失校验和时预览带「未校验」标记。
- 警告结构：断言警告是结构化 code 而不是裸字符串。
- 遗留定义降级：断言读到 native 协议定义时返回「不兼容 + 需重装」，且不产生进程启动。
- 已安装插件统一从 `app_extensions` 三表读取：断言旧分裂表不再存在。

### 接缝二（结构，复用既有）：迁移后的表清单与迁移命名断言

复用仓库已有的"表存在/不存在"清单式断言，扩展覆盖 `agent_%` 与 `app_%`：

- 断言全部 8 张旧分裂表（`agent_installations`、`conversation_adapter_packages`、`conversation_adapter_package_versions`、`conversation_adapter_catalog_releases`、`app_agent_installations`、`app_conversation_adapter_packages`、`app_conversation_adapter_package_versions`、`app_conversation_adapter_catalog_releases`）均已不存在。
- 断言统一插件市场三表（`app_extensions`、`app_extension_versions`、`app_extension_catalog_releases`）存在且存量数据无损迁入。
- 断言 `migrations/` 下所有文件名版本号均为 14 位数字，且存量 12 位 `_sqlx_migrations` 账本能被无感自愈升级。
- 断言目录契约中不再出现 `system` / `uvx` 分发类型（目录校验测试）。

### 前端测试

- 市场列表与预览对话框：断言只渲染本平台候选、跨平台进入折叠区、不可用行展示原因文案、警告渲染为中文而不是 code。

## Further Notes

### 为什么这批东西会留下来

这条链路上发生过两次结构性切换，两次都只完成了"新路径上线"，没有完成"旧路径下线"：

1. **租户级 → 应用级**：Agent 安装与会话适配器包从带租户维度迁到应用级，新表建好、数据搬完、代码切走，但旧表从未 DROP。后续的一次清理迁移甚至只对旧表执行了 `DELETE`（只清数据不删表），进一步说明"它还活着"是错觉。
2. **Native → ACP**：AntiGravity 曾是唯一的 Native 例外，改成官方 ACP 接入后，Native 后端没有回收。相关规划文档里仍写着"AntiGravity 为现有 Native Agent"，与当前事实相反。

两次切换的共同点是：**没有"切换即删除"的强制门禁**，也没人在切换后回头核对表清单。

### 建议的落地顺序

1. 决策 7（警告结构化）+ 决策 8（前端渲染）—— 用户可见收益最快，改动面最小。
2. 决策 6（候选契约扩展）+ 决策 3（分发类型收敛）—— 两者共用同一层选择器，一起改最省。
3. 决策 2（Native 退场第一步）—— 独立可验证。
4. 决策 4（删除遗留迁移）—— 依赖决策 3 完成。
5. 决策 1（表清退）—— 需要备份步骤，放在最后，单独一次可回滚的提交。
6. 决策 5（目录真相源 + 发布证据）—— 需要重新生成 bundled 目录与证据，涉及发布流程，建议独立迭代。
